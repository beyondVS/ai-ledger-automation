# Research & Decisions: Cost Control Engine Core Implementation

## Decisions & Rationale

### 1. 사업자등록번호(BRN) 부분 누락 또는 오인식 시의 대응
* **결정사항 (Decision)**: 즉각 LLM 폴백 실행
* **타당성 (Rationale)**: 10자리 사업자등록번호가 영수증 이미지/PDF 훼손으로 인해 일부 누락되거나 잘못 인식된 경우, 정적 우회 파서를 억지로 실행하면 잘못된 템플릿과 매핑되거나 엉뚱한 정규식이 가동되어 데이터가 파손될 위험이 큽니다. 따라서 식별 번호가 불완전하면 우회 시도를 포기하고 안정성이 확보된 LLM 파서로 즉시 넘겨 정합성을 보장합니다.
* **고려된 대안 (Alternatives considered)**:
  * *가맹점 상호명 기반 2차 매핑*: 사업자번호가 깨졌더라도 "스타벅스", "이마트" 등 가맹점명을 텍스트 내에서 검색하여 템플릿 매핑을 계속 시도하는 방안입니다. 그러나 상호명이 매우 보편적이거나 여러 지점의 영수증 레이아웃이 미세하게 다를 경우, 잘못된 정규식이 매핑되어 분석 오류가 발생할 리스크가 높으므로 최종 기각되었습니다.

### 2. 자가 학습 산출 정규식의 사전 검증
* **결정사항 (Decision)**: 원본 텍스트 적용 테스트 수행
* **타당성 (Rationale)**: LLM이 새로운 가맹점 분석 완료 후 자율 학습을 통해 정규식을 산출했을 때, 이를 무조건 데이터베이스에 저장하면 정합성이 훼손된 정규식이 누적되어 관리자의 검토 오버헤드를 높입니다. 따라서 백엔드 저장 전에 생성된 정규식을 해당 영수증 원본 텍스트에 임시로 매칭 테스트해보고, 추출된 필드 정보가 LLM 파싱 결과와 100% 일치할 때만 `is_verified: false`로 데이터베이스에 저장(제안)하고, 실패할 경우 폐기함으로써 데이터 무결성을 보장합니다.
* **고려된 대안 (Alternatives considered)**:
  * *단순 정규식 문법 정합성만 검증*: 파이썬 `re.compile()`을 통해 컴파일 에러 여부만 검증하는 대안입니다. 문법적 오류는 잡을 수 있으나 실제 영수증 텍스트에서 올바른 금액이나 품목을 가져올 수 있는지 논리적 검증은 불가능하므로 기각되었습니다.
  * *검증 없이 일차 저장*: LLM이 추출한 정규식을 아무런 검증 없이 저장한 후 전적으로 관리자의 수동 검토에 의존하는 방안입니다. 쓰레기 데이터 유입량이 많아져 어드민 관리 오버헤드가 지나치게 증가하므로 기각되었습니다.

### 3. LLM 폴백 처리의 동기/비동기 아키텍처
* **결정사항 (Decision)**: Celery 비동기 백그라운드 태스크 격리
* **타당성 (Rationale)**: 정적 템플릿 우회 파서가 작동했다가 실패하여 LLM으로 폴백해야 하는 경우, 이를 사용자 API 요청 스레드 내에서 동기로 처리하면 수 초 이상의 응답 지연(Network Latency)이 발생하여 UI가 블로킹되고 웹 서버 가용성이 크게 저하됩니다. 헌법 제II조(비동기 큐 전환)에 근거하여 사용자에게는 작업 접수(`202 Accepted` 및 `job_id`)를 신속하게 반환하고, 무거운 LLM 폴백 연산은 Celery 백그라운드 태스크로 완전히 격리 실행하여 시스템 처리량과 가용성을 보장합니다.
* **고려된 대안 (Alternatives considered)**:
  * *API 스레드 내 동기 처리*: 요청 즉시 완결된 파싱 결과를 응답하여 프론트엔드의 상태 관리 복잡도를 낮추는 대안입니다. 그러나 LLM API 호출 병목 시 API Gateway 커넥션 타임아웃 위험이 크고, 동시 유입 증가 시 웹 스레드가 고갈되므로 기각되었습니다.

### 4. PDF 파일 인입 시의 분석 파이프라인
* **결정사항 (Decision)**: PDF 바이트 데이터 그대로를 Gemini API 네이티브 application/pdf 파트로 직접 전달 (헌법 제I조 준수)
* **타당성 (Rationale)**: PDF 영수증이 유입될 때 Pillow 등의 이미지 변환기를 거쳐 이미지 형태로 LLM에 보내는 경우, 변환 연산 부하가 증가하고 해상도 손상으로 글자가 오인식되는 문제가 발생합니다. PDF 원본 바이트를 그대로 Gemini API의 멀티모달 application/pdf 파트로 분석시킴으로써 파싱 정합성을 극대화하고 전처리 리소스 점유를 최적화합니다.
* **고려된 대안 (Alternatives considered)**:
  * *Pillow 이미지 렌더링 전처리 후 이미지 분석*: PDF를 PNG 이미지로 변환한 후 OCR/LLM 분석을 수행하는 대안입니다. 텍스트 레이어가 온전히 살아있는 원본 PDF에 대해 불필요한 이미지 렌더링 연산을 수행하는 낭비가 있어 기각되었습니다.
