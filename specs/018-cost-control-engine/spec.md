# Feature Specification: Cost Control Engine Core Implementation

**Feature Branch**: `018-cost-control-engine`

**Created**: 2026-06-11

**Status**: Draft

**Input**: User description: "비용 통제 엔진 핵심(뼈대) 구현. `MerchantTemplate` 모델에 검증 여부(`is_verified`) 컬럼 추가 설계. 10자리 사업자등록번호를 추출하여 가맹점을 식별하고, `is_verified: true` 상태인 경우에만 LLM 호출을 우회(Bypass)하여 파싱하며 실패 시 LLM으로 폴백(Fallback)하는 기본 안전장치 구축. 신규 가맹점은 LLM 파싱 성공 후 정규식 규칙을 산출해 `is_verified: false` 상태로 자동 제안(자가 학습)하는 등록 파이프라인 구현."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 검증된 가맹점 템플릿에 대한 LLM 우회(Bypass) 파싱 (Priority: P1)

이미 시스템에 정규식 매칭 규칙이 등록되어 있고 신뢰성이 검증된 가맹점에 대해서는, 매번 비용이 들고 응답이 상대적으로 느린 LLM API를 호출하지 않고 로컬 정적 정규식 파서만을 이용해 즉시 결제 데이터를 추출 및 적재합니다.

**Why this priority**: 유료 멀티모달 LLM API 호출에 수반되는 예산 소비를 0원에 수렴하도록 완벽히 차단하고 정적 파싱하는 것이 이 비용 통제 피처의 핵심 목적이기 때문에 최우선 순위로 지정합니다.

**Independent Test**: `is_verified: true` 상태와 올바른 정규식 파싱 규칙이 등록된 가맹점의 10자리 사업자등록번호가 결제 데이터(영수증 텍스트 등)에 포함되어 매칭되는 경우, LLM 호출 로그가 발생하지 않으며 정적 파싱 규칙에 의해서만 결제 금액, 거래 일시, 품목 등이 100% 정상 파싱 및 가계부에 영속화되는지 검증합니다.

**Acceptance Scenarios**:

1. **Given** 10자리 사업자등록번호(`123-45-67890`)를 키로 하며 `is_verified: true`이고 정상 정규식 추출 규칙을 가진 `MerchantTemplate`이 존재할 때, **When** 해당 사업자번호가 추출된 영수증 데이터 파싱이 요청되면, **Then** 시스템은 LLM API를 전혀 호출하지 않고(우회) 해당 정규식 규칙에 따라 데이터를 안전하게 파싱하여 가계부 적재 트랜잭션을 성공적으로 완료해야 합니다.
2. **Given** 가맹점의 사업자번호에 부합하는 `MerchantTemplate`이 존재하나 `is_verified: false`(자가 학습 제안 상태)인 경우, **When** 영수증 데이터 파싱이 요청되면, **Then** 시스템은 정적 우회 파서를 무시하고 LLM API를 호출하여 파싱 프로세스를 수행해야 합니다.

---

### User Story 2 - 우회 파싱 실패 시 LLM 폴백(Fallback) 기본 안전장치 (Priority: P2)

가맹점 사업자등록번호가 매칭되어 `is_verified: true`인 템플릿으로 정적 파싱을 시도했으나, 가맹점의 영수증 발행 포맷이 변경되었거나 예외 텍스트가 유입되어 정적 매칭에 실패하는 경우, 에러를 반환하는 대신 즉각 LLM API 파서로 폴백하여 영수증 데이터 추출을 완수합니다.

**Why this priority**: 정적 템플릿의 취약점인 레이아웃 유연성 결여를 보완하여, 가계부 데이터 적재의 신뢰성과 데이터 무결성을 실시간으로 보장하기 위함입니다.

**Independent Test**: 검증된 가맹점(`is_verified: true`)이지만 템플릿 정규식 규격에 맞지 않는 조작된 영수증 텍스트를 인입시켰을 때, 정적 파싱 과정에서 실패 예외가 기록되고 즉시 자동으로 LLM 파서가 동작하여 정상적으로 최종 결제 레코드가 생성되는지 확인합니다.

**Acceptance Scenarios**:

1. **Given** `is_verified: true`인 `MerchantTemplate`이 매칭되었으나 영수증 레이아웃의 비직관적인 변화로 인해 정적 정규식 파싱이 실패했을 때, **When** 파싱 엔진이 기동되면, **Then** 시스템은 파싱 실패 로그를 유기적으로 남기고, 즉각 LLM API 파서로 폴백(Fallback)하여 파싱을 정상 완수하고 가계부에 기록해야 합니다.
2. **Given** 정적 우회 파서 실패 후 LLM 폴백 파서마저 예외를 던지며 최종 실패하는 최악의 조건이 발생했을 때, **When** 파싱 연산이 실행되면, **Then** 시스템은 장애 세부 로그를 적재하고 전체 데이터베이스 트랜잭션을 atomic하게 롤백하여 가계부 데이터의 불완전 적재(파편화)를 원천 차단해야 합니다.

---

### User Story 3 - 신규 가맹점 규칙 산출 및 자가 학습 등록 파이프라인 (Priority: P3)

시스템에 등록되지 않은 가맹점 영수증이 유입되어 LLM이 성공적으로 파싱을 완료한 경우, 해당 가맹점의 사업자등록번호와 원본 텍스트 레이아웃을 바탕으로 정규식 파싱 규칙을 스스로 산출하여, 차기 결제부터 활용할 수 있도록 미승인 검증 상태(`is_verified: false`)의 가맹점 템플릿 제안서로 자동 삽입합니다.

**Why this priority**: 관리자가 수백 수천 개의 다양한 가맹점 정규식 패턴을 일일이 수동 코딩하는 오버헤드를 자동화하고, 시스템이 실제 사용자의 데이터를 기반으로 자율적으로 파싱 템플릿 데이터베이스를 학습 및 확장하기 위함입니다.

**Independent Test**: 새로운 가맹점 영수증 데이터를 전송하여 LLM으로 성공적으로 파싱한 후, 데이터베이스의 `MerchantTemplate` 테이블에 해당 가맹점의 10자리 사업자등록번호와 생성된 정규식 추출 규칙이 `is_verified: false` 필드로 한 치의 오차 없이 자동 생성되는지 검증합니다.

**Acceptance Scenarios**:

1. **Given** 템플릿이 등록되지 않은 신규 가맹점의 영수증 데이터가 유입되었을 때, **When** LLM 파서가 분석에 성공하고 10자리 사업자등록번호가 올바르게 획득되면, **Then** 시스템은 해당 레이아웃 텍스트 패턴을 기초로 정규식 매칭 규칙을 스스로 도출하여 `is_verified: false` 상태인 `MerchantTemplate` 레코드를 자동 생성해야 합니다.
2. **Given** 자가 학습에 의해 생성된 미검증 템플릿(`is_verified: false`)은, **When** 관리자가 관리자 페이지에서 정적 정규식의 안전성을 수동 검증 후 승인(`is_verified: true`) 처리하기 전까지는, **Then** 다음 결제 유입 시에도 절대 우회 파서로 동작하지 않고 LLM 파서를 계속 거치도록 강력하게 통제 격리되어야 합니다.

---

### Edge Cases

- **사업자등록번호(10자리) 추출 불완전성:** 영수증 이미지나 PDF 훼손으로 사업자번호 10자리 중 일부가 누락되거나 잘못 인식되는 경우, 가맹점을 오식별하여 엉뚱한 정적 템플릿을 잘못 매핑할 위험이 있습니다. 이를 원천 차단하기 위해 사업자번호가 불완전하게 감지되면 정적 우회 시도를 포기하고 즉각 LLM 파서로의 안전한 폴백(Fallback)을 즉시 실행합니다.
- **잘못 도출된 자가 학습 정규식 규칙:** LLM 파싱 성공 후 산출된 정규식이 지나치게 관대하거나 잘못 설계되어 차후 승인 시 오동작할 위험이 있습니다. 이를 방어하기 위해 자동 도출된 정규식을 해당 영수증 원본 텍스트에 백엔드 임시 매칭 테스트를 선제 수행하며, LLM 파싱 원본 결과값과 100% 일치할 경우에만 `is_verified: false` 상태의 신규 `MerchantTemplate`으로 데이터베이스에 제안(저장)하고 실패 시 조용히 폐기합니다.
- **LLM 폴백 지연 현상:** 정적 파싱에 실패하여 LLM으로 폴백 시, 실시간 API 응답 지연이 수 초 이상 늘어나 사용자 인터페이스 반응 속도를 심각하게 떨어뜨릴 수 있습니다. 이를 방어하기 위해 우회 파싱 실패 후 실행되는 LLM 폴백 전체 프로세스를 Celery 비동기 백그라운드 태스크 큐로 안전하게 격리 처리하며, 사용자 API 호출 스레드에서는 즉시 '접수 완료(Pending)' 상태를 반환하도록 설계합니다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `MerchantTemplate` 모델은 가맹점의 검증 상태를 나타내는 `is_verified` 컬럼(Boolean, 기본값 `false`)을 반드시 포함해야 합니다.
- **FR-002**: 파싱 엔진은 유입된 결제 텍스트로부터 정규화된 10자리 사업자등록번호(BRN, 하이픈 제거 또는 공백 제거된 10자리 숫자 형식)를 정확하게 추출해야 합니다.
- **FR-003**: 추출된 사업자등록번호를 기반으로 데이터베이스에서 매치되는 `MerchantTemplate`을 검색하고, 오직 해당 템플릿의 `is_verified` 속성이 `true`인 경우에만 LLM 파서 호출을 우회(Bypass)하여 정적 정규식 파싱을 실행해야 합니다.
- **FR-004**: `is_verified: true`인 가맹점 템플릿이 존재하지 않거나, 매칭에 성공해 정적 우회 파서를 기동했음에도 파싱 에러(필수 필드 누락 등)가 발생하는 경우, 즉시 LLM 파서로의 안전한 전환(Fallback)이 이루어지는 파이프라인 안전장치를 구현해야 합니다.
- **FR-005**: 템플릿이 등록되지 않은 신규 가맹점 영수증을 LLM 파서가 성공적으로 파싱한 경우, 파싱된 항목 정보(금액, 가맹점명 등)와 원본 텍스트의 구조적 매칭 구조를 대조하여 템플릿용 정규식 추출 규칙을 자동 제안할 수 있는 규칙 생성 로직을 구동해야 합니다.
- **FR-006**: 자가 학습에 의해 산출된 규칙은 `is_verified: false` 상태의 신규 `MerchantTemplate`으로 데이터베이스에 즉시 자동 제안 형태로 삽입되어야 합니다.

### Key Entities *(include if feature involves data)*

- **MerchantTemplate (가맹점 템플릿)**: 가맹점을 식별하기 위한 고유 키인 10자리 사업자등록번호, 정적 파싱을 위한 필드별 정규식 매칭 규칙 세트, 관리자 검증 완료 여부(`is_verified`) 상태를 영속화하는 엔티티입니다.
- **CostControlParser (비용 통제 파서 엔진)**: 결제 원본 텍스트로부터 사업자번호 매칭, `is_verified` 검증, 정적 우회 파서 실행, 예외 포착 시 LLM 폴백 처리 및 자가 학습 규칙 생성 파이프라인 전반을 관리하는 통합 코어 컨트롤러입니다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 검증 완료(`is_verified: true`) 상태인 기존 가맹점 결제 데이터 유입 시, LLM API 호출 횟수를 실질적으로 0회로 통제(100% 우회)해야 합니다.
- **SC-002**: 정적 우회 파서 매칭이 실패하여 LLM 파서로 폴백되는 예외 상황에서도 가계부 적재 실패가 없어야 하며, 최종 데이터베이스 원자적 적재 성공률 99% 이상을 보장해야 합니다.
- **SC-003**: 자가 학습 파이프라인을 거쳐 생성된 신규 가맹점의 `MerchantTemplate` 레코드는 오직 `is_verified: false` 상태로만 데이터베이스에 기입되어 승인 전 자동 유출률 0%를 유지해야 합니다.
- **SC-004**: 정적 정규식 우회(Bypass) 파싱 성공 시, 백엔드 데이터 파싱 및 응답 생성 총 소요 시간을 100ms 이하로 달성하여 인프라 반응성을 극대화해야 합니다.

## Assumptions

- 10자리 사업자등록번호는 공백이나 하이픈 등 기호 형태와 관계없이 순수 숫자 10자리 문자열로 정규화되어 가맹점 식별 키로 비교 적용됩니다.
- PDF 형식의 파일 인입 시, Pillow 이미지 변환 전처리를 완전히 우회하고 PDF 바이트 데이터를 그대로 Gemini API의 `application/pdf` 파트를 통해 네이티브하게 전송하여 텍스트를 추출하는 것으로 전제합니다.
- 자가 학습 파이프라인을 통해 산출되어 `is_verified: false`로 등록된 템플릿은 가동 중인 비용 통제 엔진에 어떠한 사이드 이펙트도 주지 않으며, 어드민을 통해 검증이 활성화된 경우에만 정적 엔진 매핑 대상에 편입됩니다.
