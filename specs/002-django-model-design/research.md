# Research: Django Model Design Decisions for AI Ledger

본 연구 보고서는 AI 가계부 자동화 시스템의 핵심 데이터 모델 수립을 위해 수행된 아키텍처적 연구 성과와 핵심 기술 의사결정을 기술합니다. 헌법 제약 조건(v1.2.0) 및 피처 명세서(`spec.md`)의 비즈니스 성공 기준을 철저하게 만족하는 견고한 데이터 모델 레이아웃 설계를 수립하였습니다.

---

## 1. 결정사항 (Decision): PostgreSQL v18 Native UUIDv7 기본 키(Primary Key) 채택

### 타당성 (Rationale)
- **시계열 인덱스 성능 최적화**: UUIDv7은 타임스탬프 정보가 상위 비트에 순차적으로 배치되므로, 생성 시간 순서대로 자연스럽게 물리적인 정렬이 가능합니다. 이로 인해 임의의 순서로 적재되는 UUIDv4 대비 PostgreSQL B-Tree 인덱스 쓰기 성능 저하(Page Split)가 발생하지 않습니다.
- **월별 지출 통계 쿼리 최적화**: UUIDv7은 시계열 인덱스 특성을 가져 최근 트랜잭션 데이터를 매우 빠르게 조회할 수 있어, 월별 통계 분석이나 최근 결제 내역 조회 시 스캔 범위를 비약적으로 단축시킵니다.
- **분산 환경의 정합성**: 다중 컨테이너 및 복수 비동기 Celery 워커 환경에서 데이터베이스 시퀀스 락(Sequence Lock)에 대한 경합 없이 고유한 PK를 독립적으로 발급할 수 있습니다.
- **PostgreSQL v18+ 최적 성능 활용**: PostgreSQL v18에서 지원하는 Native UUIDv7 생성 함수 및 인덱스 정렬 I/O 성능 극대화 이점을 고스란히 획득합니다.

### 고려된 대안 (Alternatives considered)
- **Auto-increment Integer (BigAutoField)**: 데이터베이스가 단일 물리 노드에서 확장될 때 sequence 락 경합 병목이 발생하고, 데이터베이스 분할(Sharding)이나 마이그레이션 병합 시 기본 키 충돌 가능성이 매우 높습니다.
- **UUIDv4**: 완전히 무작위(Random)로 생성되므로, 데이터베이스 B-Tree 인덱스 삽입 시 랜덤 쓰기가 빈번히 발생하여 대용량 적재 시 인덱스 파편화 및 심각한 I/O 성능 고갈을 유발합니다.

## 2. 결정사항 (Decision): Django ORM `transaction.atomic()`을 활용한 원자적 1:N 트랜잭션 적재 및 복합 UNIQUE 키 중복 방지

### 타당성 (Rationale)
- **강력한 데이터 원자성(Atomicity) 수호**: 영수증 1장을 분석 및 파싱하여 마스터 레코드(`Ledger`)와 복수의 상세 품목 레코드(`LedgerItem`)를 인서트할 때, 하나라도 데이터베이스 제약에 위배되거나 네트워크 지연이 발생할 경우 전체를 롤백(`transaction.atomic()`)하여 데이터 파편화(Dirty State)를 기계적으로 차단합니다.
- **중복 유입의 데이터베이스 레이어 원천 차단**: 통계 왜곡 및 불필요한 스토리지 낭비를 방지하기 위해 `UNIQUE (user_id, vendor_registration_number, transaction_date, total_amount)` 복합 고유 제약조건을 데이터베이스 레이어에 물리적으로 강력하게 적용합니다. 이를 통해 애플리케이션 단의 미세한 레이스 컨디션 우려를 사전에 배제합니다.
- **연쇄 삭제 무결성**: 부모 가계부 레코드(`Ledger`)가 삭제될 시, 이에 매핑된 `LedgerItem`은 `ON DELETE CASCADE`를 통해 완벽히 연쇄적으로 소멸하도록 설계하여 쓰레기 데이터 누수를 원천 방어합니다.

### 고려된 대안 (Alternatives considered)
- **애플리케이션 단의 조회 후 삽입 (Read-Then-Write)**: 고용량 비동기 큐나 사용자의 연속 터치로 동시 요청이 유입될 시, 데이터베이스에 인서트되기 전 정합성 검사를 지나쳐 버리는 미세한 타임 슬롯(Race Condition)이 발생하여 중복 데이터 적재를 차단하지 못합니다.
- **비원자적 비동기 분할 적재**: Ledgers를 먼저 커밋하고 LedgerItems를 비동기식으로 천천히 밀어 넣는 설계는, LedgerItems 적재 실패 시 가계부 총합과 상세 항목 간의 수치 불일치 장해를 빈번히 유발하여 가계부 금융 데이터 신뢰성을 훼손하므로 배제하였습니다.

## 3. 결정사항 (Decision): `MerchantTemplate`의 `is_verified` 격리 통제 필터 및 `FailedTask` (Dead Letter Queue) 도입

### 타당성 (Rationale)
- **비용 최적화 우회 파서의 오염 원천 차단**: 10자리 사업자등록번호 기반 정적 정규식 캐싱 규칙(`MerchantTemplate`)은 유료 LLM 비용을 0원에 수렴시키는 핵심 파이프라인입니다. 그러나 기계적으로 자율 제안되는 정규식 후보군이 오동작을 일으켜 전체 사용자 지출 데이터를 훼손하는 사태를 예방하기 위해, 수동 승인 마크(`is_verified: true`)가 획득된 정규식만 우회 바이패스에 반영하고 미검증 규칙(`is_verified: false`)은 완벽하게 필터링 차단합니다.
- **비동기 큐 및 DB 리소스 보존**: 비동기 파싱 실패나 예외 장해 유발 시 무작정 재시도(Retry Retry)를 반복하는 대신 `FailedTask` 테이블에 원시 무가공 텍스트 및 오류 콜스택 로그를 즉시 격리 기록(Dead Letter Queue)하여 백그라운드 큐 리소스의 고갈 붕괴를 사전에 제어합니다.

### 고려된 대안 (Alternatives considered)
- **자율 제안 템플릿 즉시 반영**: 정밀한 휴먼-인-더-루프(Human-in-the-loop) 검증 단계를 거치지 않을 경우, 영수증 폰트 훼손이나 파서 오류로 잘못 추출된 정규식 레이아웃 캐시가 전체 사용자 동일 사업자 가맹점의 데이터 변환을 장기적으로 오염시키는 초대형 런타임 장해를 유발할 우려가 있습니다.
- **영수증 파일 예외 시 로컬 파일 로깅 및 무한 재시도**: 무한 재시도는 supabase 가용한계 커넥션 풀을 급격히 점유하고 CPU 부하를 발생시키며, 비정형 파일 예외 로그 유실로 인해 원인 분석에 어려움을 겪으므로 배제하였습니다.
