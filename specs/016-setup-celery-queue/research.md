# Research Notes: Celery 비동기 작업 큐 및 Docker 통합 개발 환경

## 결정사항 및 모범 사례 (Decisions & Best Practices)

### 1. Docker Compose 환경에서의 핫 리로딩 (Hot-Reloading)
- **결정**: Django 백엔드 및 Vue3 프론트엔드 컨테이너 전체에 볼륨 바인드 마운트(`volumes`)를 적용하고 개발 서버 핫 리로딩을 연동합니다.
- **타당성**: 개발자가 로컬에서 소스를 편집할 때 매번 컨테이너를 빌드 및 기동하는 수동 리스크를 제거하여 개발 피드백 루프를 크게 단축시킵니다.
- **대안**:
  - *컨테이너 빌드 자동화(Watchtower 등)*: 핫 리로딩 대비 반영 Latency가 10초 이상으로 느려서 개발 환경에는 부적합하여 기각.
- **Windows-Docker 파일 감지 이슈 방어**:
  - Windows 호스트에서 볼륨 마운트 시 WSL2 경계를 넘어가면서 `inotify` 파일 변경 이벤트가 컨테이너 내의 Vite dev server로 전파되지 않는 문제가 있습니다.
  - 이를 해결하기 위해 프론트엔드 `vite.config.js`의 `server.watch` 설정에 `usePolling: true` 및 `interval: 100`을 강제 명시하여 변경을 감지하도록 보장합니다.

### 2. Django 및 Celery 데이터베이스 커넥션 풀 통제
- **결정**: 헌법의 자원 최적화 조항에 따라 최대 DB 커넥션 풀 크기를 백엔드 API 서버 최대 5개, Celery 워커 최대 3개로 제약합니다.
- **타당성**: Supabase/AWS 프리티어 등 최대 max_connections가 20개 내외로 극소한 인프라 환경에서 커넥션 누수로 인한 DB 붕괴를 원천 방지합니다.
- **대안**:
  - *커넥션 풀 제약 없음*: 트래픽 일시 폭증 시 워커가 모든 커넥션을 고갈시켜 API 서버 전체의 서비스 불능을 야기하므로 기각.
- **구현 방식**:
  - Django `DATABASES` 설정 내에 `CONN_MAX_AGE`를 적절히 튜닝하여 연결 재사용률을 제어하고, DB 연결 수명이 무한히 유지되어 고갈되는 것을 방지합니다.
  - Celery 실행 시 `--concurrency=3` 등의 옵션을 부여하고 워커 프로세스당 연결 수를 제한합니다.

### 3. 비동기 작업 상태 조회 (Polling)
- **결정**: 프론트엔드는 HTTP 2초 간격의 숏 폴링(Short Polling)을 가동하고, 최대 30초 대기 후 타임아웃 처리합니다.
- **타당성**: 웹소켓(Websocket)이나 SSE(Server-Sent Events)에 비해 구조가 단순하고 오버헤드가 적으며, DB 커넥션 및 프로세스 리소스를 점유하지 않습니다.
- **대안**:
  - *Websocket/SSE*: 실시간성은 우수하나 상시 커넥션 연결을 유지해야 하므로, Supabase Free plan 및 컨테이너 가용 풀을 고려할 때 자원 낭비가 심해 기각.

### 4. Celery 비동기 작업 실패 시 자동 재시도
- **결정**: 외부 API(Gemini, SendGrid 등) 호출 실패 시 최대 3회 자동 재시도하며, 지수 백오프(`Exponential Backoff`)를 적용합니다.
- **타당성**: 외부 통신의 순간적인 타임아웃 및 순단 장애로 인한 가계부 누락 예외를 자율 복구하여 비동기 데이터의 최종 일관성을 보장합니다.
- **대안**:
  - *즉시 실패 처리*: 일시적 네트워크 장애에도 사용자가 재업로드해야 하는 불편을 초래하므로 기각.
