# Research and Architecture Decisions: Receipt Async Load Testing

본 문서는 3주차 비동기 아키텍처 튜닝 및 부하 테스트를 위해 내려진 주요 아키텍처 결정사항과 그 타당성(Rationale), 그리고 기각된 대안을 기술합니다.

---

## 1. Celery 비동기 워커 동시성 및 프리페치 제어

* **결정사항 (Decision)**: 
  Celery 비동기 워커 프로세스의 동시성(Concurrency) 한도를 최대 3개로 설정(`CELERY_WORKER_CONCURRENCY=3`)하고, 개별 워커의 태스크 프리페치 개수(`CELERY_WORKER_PREFETCH_MULTIPLIER=1`)를 1로 제한합니다.
* **타당성 (Rationale)**:
  프로젝트 헌법 제II조에 의거하여, Supabase Free-tier 및 로컬 DB의 최대 데이터베이스 커넥션 풀 크기는 비동기 워커당 3개, 전체 합산 8개 이하로 엄격히 통제됩니다. 만약 Celery 워커가 제한 없이 스레드를 늘려 50개의 영수증을 동시 처리하려고 시도하면, RDBMS 측에서 `OperationalError: connection limit exceeded` 예외를 발생시키며 트랜잭션이 마비되거나 누락되는 심각한 장해가 발생합니다. 동시성을 3으로 제한하고 프리페치를 1로 통제하면, 워커는 한 번에 정확히 최대 3개의 작업을 안정적으로 순차 소화하여 커넥션 고갈을 원천 차단합니다.
* **고려된 대안 (Alternatives considered)**:
  * *대안 A*: Celery 동시성을 10 이상으로 늘리고 PostgreSQL 최대 커넥션을 상향 조정.
    * *기각 사유*: 인프라 비용(Supabase Free-tier 물리적 제한) 조건에 위배되며, 로컬 자원 소모량이 지나치게 커져 비용 최적화 원칙에 어긋남.

## 2. 부하 테스트용 Mock API 파이프라인 구성

* **결정사항 (Decision)**:
  50종의 대량 영수증 부하 테스트 자동화 실행 시, 네트워크 레이어 또는 LiteLLM Router 레이어에서 Ollama 및 Gemini API 호출을 모킹(Mocking)하여 기 설정된 모의 JSON 응답(ReceiptSchema 규격)을 반환하는 테스트 전용 드라이버를 구성합니다.
* **타당성 (Rationale)**:
  실제 Gemini 2.5 API를 사용하여 50종 부하 테스트를 매 린팅/통합 테스트마다 실행할 경우, 대량의 외부 API 네트워크 비용이 청구되고 분당 요청 제한(Rate Limit)에 걸려 빌드 및 테스트 파이프라인이 즉시 마비됩니다. 3단계 하이브리드 파이프라인의 핵심인 '연결 및 롤백 신뢰성'과 '중복 제거 로직의 병렬 내성'을 검증하기 위해서는 API 응답의 신속하고 일관된 목업화가 필수적입니다.
* **고려된 대안 (Alternatives considered)**:
  * *대안 B*: 실제 개발/테스트용 유료 API Key를 할당해 매번 실서버 호출.
    * *기각 사유*: 분당 API 한도 초과로 인한 테스트 오작동 및 통제 불가능한 API 비용 누수 발생.

## 3. 트랜잭션 롤백 무결성 검증을 위한 의도적 실패 주입

* **결정사항 (Decision)**:
  부하 테스트용 50종 데이터셋 중 10%에 해당하는 5종에 대해 일부러 손상된 이미지 파일 또는 필수 스키마 정보가 결여된 Mock 영수증을 주입하여, 이들이 비동기 파이프라인 상에서 에러를 뿜었을 때 다른 45종의 정상 처리에 영향을 미치지 않고, 실패한 5종만 정확히 롤백되어 DB에 찌꺼기 레코드가 전혀 남지 않음을 검증합니다.
* **타당성 (Rationale)**:
  부하 환경에서 트랜잭션 격리 수준 및 원자성이 정상적으로 유지되는지 검증하기 위해서는 정상 경로(Happy Path)뿐만 아니라 실패 경로(Failure Path)가 섞인 환경에서도 격리성(Isolation)이 지켜지는지 확인해야 합니다. `transaction.atomic()`의 원자적 동작을 E2E 환경에서 입증하는 가장 직관적이고 확실한 검증 설계입니다.
* **고려된 대안 (Alternatives considered)**:
  * *대안 C*: 수동 스크립트를 통해 에러가 난 ID를 추적해 Delete 쿼리로 지우는 방식.
    * *기각 사유*: 데이터베이스 엔진 레벨의 원자성(ACID)을 검증할 수 없으며, 테스트 실행 도중 프로세스가 비정상 종료될 때 DB가 오염되는 현상을 막지 못함.
