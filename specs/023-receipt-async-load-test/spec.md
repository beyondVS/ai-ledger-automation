# Feature Specification: Receipt Async Load Testing

**Feature Branch**: `023-receipt-async-load-test`

**Created**: 2026-06-17

**Status**: Draft

**Input**: User description: "3주차 비동기 아키텍처 튜닝 및 부하 테스트. 웹 업로드 경로로 유입되는 영수증 50종 일시 유입 부하 테스트를 통해 데이터 누락 및 트랜잭션 정합성 검증 완료."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 영수증 50종 일시 업로드 및 비동기 처리 (Priority: P1)

사용자는 가계부 서비스의 대량 업로드 기능을 통해 50장의 영수증 이미지를 일시에 선택하여 업로드합니다. 시스템은 클라이언트의 웹 화면이 굳거나 커넥션 타임아웃이 발생하지 않도록 신속하게 업로드 성공 응답을 내려주고, 백그라운드 비동기 큐를 통해 대량의 영수증 파싱 작업을 유실 없이 처리합니다.

**Why this priority**: 동시 다발적인 대량 영수증 유입 환경에서도 API 서비스가 중단되지 않고 대기 시간 없이 원활하게 비동기로 작업을 소화할 수 있게 하는 핵심 MVP 사용자 경험입니다.

**Independent Test**: 50개의 모의 영수증 이미지를 포함한 벌크 업로드 API 요청을 전송하여, 클라이언트가 5초 이내에 HTTP 202 Accepted 등의 즉각적인 접수 응답을 받고, 백그라운드 Celery 큐에 50개의 비동기 태스크가 정상 안착하여 가동되는지 검증합니다.

**Acceptance Scenarios**:

1. **Given** 50개의 규격화된 영수증 이미지 파일이 준비된 상태에서, **When** 사용자가 웹 대량 업로드 API Endpoint로 50개 파일을 일시에 전송할 때, **Then** 시스템은 요청을 즉시 접수하고 각 영수증 파일의 추적용 태스크 ID가 담긴 성공 메타데이터를 5초 이내에 클라이언트에 반환해야 한다.
2. **Given** 50개의 작업이 비동기 큐에 적재된 상태에서, **When** Celery 워커가 순차적으로 백그라운드 파싱 작업을 진행할 때, **Then** 작업 중 스레드 중단이나 작업 유실 없이 전체 50개 태스크가 최종 상태(성공 혹은 의도된 에러 상태)로 완료 수렴해야 한다.

---

### User Story 2 - 비동기 처리 중 데이터 정합성 보장 및 중복 생성 방지 (Priority: P2)

50장의 영수증이 비동기 큐에서 병렬적으로 파싱 및 적재되는 와중에도, 시스템은 동일 가맹점/동일 금액/임계 시간 내 연속 승인 등의 중복 데이터를 완벽히 식별하여 데이터베이스에 중복 생성을 차단하며, 특정 영수증 작업의 장애 발생 시 연관된 상세 내역 적재를 완벽히 롤백하여 DB 내 정보 왜곡을 예방합니다.

**Why this priority**: 금융 가계부 서비스의 가장 중요한 가치인 데이터의 무결성과 신뢰성을 수호하고, 동시성 이슈로 인한 중복 거래 데이터 적재를 방지하기 위함입니다.

**Independent Test**: 60초 이내의 동일 승인번호/동일 금액을 가진 중복 영수증 2종을 포함한 50종 데이터셋을 동시 업로드하여, 중복 방어 필터가 작동하여 데이터베이스에는 최종 1건만 안전하게 기록되는지 확인하고, 파싱 에러 발생 영수증의 경우 연관 테이블에 데이터 조각이 남지 않았는지 검증합니다.

**Acceptance Scenarios**:

1. **Given** 50종 중 60초 임계 시각 윈도우 내에 존재하는 승인번호와 결제 금액이 동일한 영수증 2종이 병렬 처리될 때, **When** 비동기 DB 적재 단계가 완료된 시점에서, **Then** 최종 데이터베이스에는 중복 레코드 생성이 차단되고 오직 1건의 가계부 마스터 레코드만 존재해야 한다.
2. **Given** 비동기 3단계 파이프라인 중 오류가 발생한 비정상 영수증 처리 과정에서, **When** 데이터베이스 적재 트랜잭션이 수행될 때, **Then** 단 하나의 장고 ORM 트랜잭션 세션 블록(`transaction.atomic()`) 내에서 원자적으로 처리되어, 전체 테이블(`ledgers` 및 `ledger_items`)의 삽입 연산이 100% 롤백되고 어떠한 부분 데이터 파편도 영속화되지 않아야 한다.

---

### User Story 3 - 부하 테스트 실행 결과 리포팅 및 모니터링 (Priority: P3)

시스템 운영자 및 테스터는 50종 부하 테스트가 완료된 이후, 각 영수증별로 어떤 파이프라인 단계(로컬 Ollama, Gemini Text 폴백, Gemini Vision 폴백)에서 성공했는지, 전체 실행 시간은 얼마나 걸렸는지, 실패한 태스크가 있다면 구체적인 사유가 무엇인지 요약된 테스트 리포트와 로그를 조회할 수 있어야 합니다.

**Why this priority**: 비동기 아키텍처 튜닝(Celery 동시성, DB 커넥션 풀 크기 등)의 성과를 객관적 수치로 증명하고, 향후 병목 구간을 빠르게 추적할 수 있도록 시각화 및 모니터링하기 위함입니다.

**Independent Test**: 부하 테스트 자동화 스크립트 실행 후, 로그 데이터 및 메트릭 데이터베이스를 쿼리하여 가시성 있는 종합 리포트 포맷이 정상 출력되는지 검증합니다.

**Acceptance Scenarios**:

1. **Given** 50종 부하 테스트가 모두 종료된 상태에서, **When** 시스템 결과 집계 모듈 또는 모니터링 로그를 확인할 때, **Then** 총 소요 시간, 각 영수증별 성공/실패 여부, 3-Tier 하이브리드 파이프라인 각 단계(Ollama / Gemini Text / Gemini Vision)의 매칭 성공률 메트릭이 정확하게 출력되어야 한다.

---

### Edge Cases

- **DB 커넥션 풀 고갈 위험 (OperationalError)**: 50종 영수증이 백그라운드에서 지나치게 높은 동시성으로 병렬 처리를 시도하여, 설정된 컨테이너 최대 커넥션 풀 크기(Celery async_worker 최대 3개, 전체 합산 8개 이하)를 초과해 데이터베이스 접근이 차단되는 현상.
  - *해결 방안*: Celery 동시성(Worker concurrency)을 최대 3개 이하로 기계적으로 제한하고, 큐 내부 대기 시간을 조절하여 DB 커넥션 획득 타임아웃을 미연에 방지합니다.
- **비정상 파일/포맷 인입**: 50종의 파일 중 손상된 이미지 파일 또는 지원하지 않는 규격의 파일이 섞여서 업로드되는 케이스.
  - *해결 방안*: 시스템은 해당 파일을 사전 검증하여 즉시 예외 상태(Failed)로 롤백 및 태스크 로그를 남기며, 이 오류가 큐의 다른 49종 영수증 처리 스레드에 어떠한 영향도 미쳐서는 안 됩니다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 웹 업로드 경로(API Endpoint)를 통해 다중 파일(최대 50개)을 단일 HTTP 멀티파트 요청으로 유실 없이 동시 접수해야 합니다.
- **FR-002**: 백그라운드 비동기 처리 중 Celery 워커는 영수증 1장마다 `ledgers` 마스터 레코드와 `ledger_items` 상세 데이터를 단 하나의 ORM 트랜잭션 세션 블록(`transaction.atomic()`) 내에서 원자적으로 처리해야 합니다.
- **FR-003**: 60초 임계 시각 윈도우 기반 중복 결제 방어 알고리즘이 비동기 다중 쓰기 상황에서도 정상적으로 작동하여, 동일 가맹점 및 금액의 데이터가 중복 생성되지 않아야 합니다.
- **FR-004**: 영수증 파싱 실패 시, 로컬 OCR/LLM(Ollama gemma4:e4b) -> Gemini 텍스트 폴백 -> Gemini 비전 폴백의 3단계 하이브리드 파이프라인이 정상적으로 동작하며, 폴백 이관 시 base64 이미지 규격 충돌 등의 예외가 없어야 합니다.
- **FR-005**: 카테고리 정보가 제공되지 않거나 데이터베이스에 존재하지 않는 유효하지 않은 카테고리 값이 유입되는 경우, 기본 카테고리를 '미분류'로 자동 강제 매핑하여 가계부 적재의 영속성을 보장해야 합니다.
- **FR-006**: 동시성 제어를 위해 비동기 워커의 최대 동시 활성 스레드 및 데이터베이스 커넥션 소모 개수를 엄격히 3개 이하로 제한 제어해야 합니다.

### Key Entities

- **ReceiptTask**: 비동기 영수증 업로드 요청마다 생성되는 관리 엔티티. 업로드 파일 식별자, 현재 진행 상태(Pending, Processing, Completed, Failed), 파이프라인 완료 단계(Ollama, GeminiText, GeminiVision), 에러 내용, 데이터베이스 트랜잭션 원자성 매핑 상태 등의 정보를 보관.
- **Ledger**: 가계부 내역 마스터 엔티티. 결제 일시, 가맹점명, 총 결제 금액, 결제 수단, 결제 승인번호 등을 포함하며 중복 검증의 대상이 됨.
- **LedgerItem**: 가계부 내역 상세 품목 엔티티. 품명, 수량, 단가, 카테고리(유효하지 않을 시 '미분류'로 매핑) 정보를 가지며, Ledger 엔티티와 트랜잭션 내에서 원자적으로 1:N 묶음 생성됨.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 50종의 영수증 벌크 업로드 요청 시, 웹 API 서버는 HTTP 202 Accepted 등의 접수 완료 응답을 5초 이내에 반환해야 합니다.
- **SC-002**: 50종 영수증 처리 완료 시점까지 DB 커넥션 타임아웃 또는 커넥션 풀 고갈로 인한 시스템 런타임 예외(OperationalError) 발생율이 0%여야 합니다.
- **SC-003**: 정합성이 맞는 정상 영수증 50종(또는 정상 분류군) 처리 시, DB에 누락된 레코드(Lost Record) 또는 유실된 필드 정보 없이 100% 영속화가 완료되어야 합니다.
- **SC-004**: 파싱 에러나 데이터 충돌 등으로 실패 판정된 영수증 건에 대해, 데이터베이스 트랜잭션 롤백 무결성이 100% 작동하여 Ledger 레코드 없이 LedgerItem만 남는 고아 데이터(Orphan Data) 발생 건수가 0건이어야 합니다.

## Assumptions

- 시스템의 DB 커넥션 풀은 Free-tier 환경을 고려하여 api-server 최대 5개, Celery 워커 최대 3개, 전체 합산 8개 이하로 기계적으로 제약되어 있습니다.
- 백그라운드 Celery 워커가 기동되는 환경에서는 로컬 Ollama 모델(`gemma4:e4b`)이 기동되어 1단계 로컬 파싱을 전담하며, 네트워크 폴백으로 외부 Gemini API(Flash v2.5)가 정상 호출 가능한 상태입니다.
- 테스트용 50종 영수증 데이터셋(정상 데이터 45종, 포맷 에러 및 중복 유발용 5종)이 사전에 `docs/receipt-example/` 또는 부하 테스트 디렉토리에 확보되어 활용된다고 가정합니다.
