# Technical Research: Production Infrastructure Optimization & Security Control

본 문서는 대규모 실 인프라용 도커 컴포즈 구성을 튜닝하는 과정에서 설계된 핵심 기술적 선택 사항들과 그 타당성을 입증한 조사 결과서입니다.

---

## 1. 외부 포트 보안 접근 제어 및 네트워크 격리

### 결정사항 (Decision)
* 외부 인터넷망(Public IP)에 노출되는 호스트 포트를 오직 역방향 프록시 게이트웨이인 **Nginx(80, 443)** 포트로만 엄격하게 한정합니다.
* 데이터베이스(PostgreSQL, 5432), 인메모리 캐시(Redis, 6379), 백엔드 API 애플리케이션(api-server, 8000) 등 나머지 모든 서비스는 `docker-compose.prod.yml` 파일의 `ports` 설정에서 바인딩을 제거하고, 내부 가상 네트워크망(`bridge` 드라이버 기반의 컴포즈 전용 격리 네트워크)을 통해서만 상호 통신하도록 설계합니다.

### 타당성 (Rationale)
* **보안 공격 면적(Attack Surface) 최소화**: 실서버 공인 IP의 포트를 외부에 노출하지 않는 것은 보안 취약점 공격(예: SQL Injection, Brute force, Redis RCE 취약점 공격 등)을 방어하기 위한 최전방 방어막입니다.
* **통제된 인그레스(Ingress)**: 모든 외부 트래픽이 웹 서버(Nginx)의 로깅, SSL 핸드셰이크, 요청 스로틀링(Rate Limiting) 레이어를 기계적으로 무조건 거치도록 강제하여 트래픽 무결성을 달성할 수 있습니다.

### 고려된 대안 (Alternatives considered)
* **호스트 방화벽(UFW 등) 제어 방식**: 5432/6379 포트를 외부로 바인딩해 두고 호스트 수준에서 특정 관리자 IP만 화이트리스트로 허용하는 대안을 검토했습니다. 그러나 도커 데몬이 시작될 때 호스트의 `iptables` 체인을 직접 조작하여 호스트 방화벽 설정을 기본적으로 우회하는 현상(Docker-UFW bypass 우회 결함)이 발생하여 보안 무력화 리스크가 존재하므로 기각되었습니다.

## 2. PostgreSQL 영속 데이터 볼륨 마운트 정책

### 결정사항 (Decision)
* 실 서비스 데이터의 영속성 보장을 위해 호스트 디렉토리 직접 지정 바인딩을 배제하고, 도커 엔진이 격리 관리하는 **도커 Named Volume (`postgres_data`)**을 사용합니다.
* 데이터 백업 및 아카이빙 요건은 백엔드 크론탭 및 별도 CLI 유틸리티를 활용하여 `docker exec pg_dump` 쿼리 기반 덤프 방식을 수행하고, 덤프된 백업 파일을 호스트의 안전 공간으로 동적 소산하는 정책을 수립합니다.

### 타당성 (Rationale)
* **UID/GID 권한 충돌 해소**: PostgreSQL 프로세스는 컨테이너 내부에서 보안상 `postgres` 고유 사용자 ID(일반적으로 999)로 기동됩니다. 호스트의 디렉토리를 직접 마운트하면 호스트 운영체제의 파일 소유 권한 정책과 엇갈려 파일 쓰기가 거부(`Permission Denied`)되고 DB가 아예 부팅되지 않는 장해가 쉽게 유발됩니다. Named Volume을 사용하면 도커가 자동으로 컨테이너 사용자 권한에 맞게 볼륨 파일 소유권을 맞추어 기동 제로-클래시를 보장합니다.
* **이식성(Portability) 증대**: 물리 서버 이전 시 호스트의 디렉토리 절대 경로 구조에 의존하지 않으므로 볼륨 메타데이터의 이관이 신속하고 안전합니다.

### 고려된 대안 (Alternatives considered)
* **호스트 디렉토리 직접 마운트 (Host Bind Mount)**: `/var/lib/postgresql/data` 등의 호스트 절대 경로에 직접 마운트하는 대안을 평가했습니다. 호스트 시스템 상에서 데이터 파일들을 물리적으로 직접 볼 수 있어 편리하지만, 앞서 언급된 파일 권한 문제 해결을 위해 호스트 디렉토리 소유권을 임의로 변경해야 하며, 호스트 OS 환경마다 보안 설정(예: SELinux, AppArmor) 권한 충돌이 추가 발생하므로 운영 안정성 면에서 부적합하다고 판단하여 기각하였습니다.

## 3. 리소스 제한 및 로그 로테이션 고정 설계

### 결정사항 (Decision)
* 각 서비스 컨테이너가 사용할 수 있는 최대 CPU 점유 가중치 및 메모리 한계값(limits/reservations)을 `docker-compose.prod.yml` 파일 내에 **절대 수치로 직접 고정(Hardcoded)** 선언합니다.
* 컨테이너들의 디스크 용량 잠식 장해를 막기 위해 도커 데몬의 기본 로깅 대신 컴포즈 개별 서비스 레이어에 `json-file` 로그 드라이버 정책을 명시하고, 파일 용량을 최대 10MB(`max-size: "10m"`), 백업 파일 보존 수를 3개(`max-file: "3"`)로 설정해 누적 로그 용량을 서비스별 30MB 이하로 통제합니다.

### 타당성 (Rationale)
* **환경 변수 누락 취약점 원천 방지**: 자원 제한을 환경 변수(`.env`)로 받아 런타임에 싱크하는 방식은, 환경 설정 동기화 유실이나 실수로 변수 주입이 비어있을 시 컴포즈가 리소스 한도 없이 `unlimited` 상태로 기동하는 맹점이 존재합니다. 빌드 파이프라인에서 정적으로 입증된 한계값을 강제(Immutable infrastructure)하는 것이 결정론적 신뢰성을 확보하는 최선입니다.
* **인프라 폭주 차단**: 특정 API 호출의 폭주나 비동기 Celery 워커의 메모리 누수 장해 발생 시에도 설정된 limits 선에서 프로세스가 격리 제어(OOM Kill/Restart)되므로, 동일 장비 내 데이터베이스 등 코어 자원의 메모리 고갈로 서버 전체가 셧다운되는 최악의 장해를 물리 방어합니다.

### 고려된 대안 (Alternatives considered)
* **동적 환경 변수 주입 방식 (Configurable limits via Env)**: 배포 서버 스펙에 대응하기 위해 리소스 제한 수치를 환경 변수로 주입받는 구조를 평가했습니다. 하지만 설정값 누락에 따른 장애 방어가 어렵고, 실 서비스 환경의 물리 장비 스펙은 기본적으로 릴리즈 시점에 고정되어 있으므로 동적 변경 유연성의 실익보다 환경 설정 휴먼 에러에 의한 보안 누락 위험이 더 크다고 판단하여 기각하였습니다.
