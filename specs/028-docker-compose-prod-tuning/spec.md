**Created**: 2026-06-23

**Status**: Draft

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 서비스 고가용성 및 자원 격리 (Priority: P1)

대규모 트래픽이 유입되거나 특정 서비스에 비정상적인 부하가 집중되더라도, 전체 컨테이너 시스템이 붕괴하지 않고 지정된 CPU 및 메모리 리소스 한도 내에서 안전하게 격리되어 기동하기를 원합니다. 또한 프로세스 장해 발생 시 무한 크래시 루프에 빠지지 않고 정해진 횟수 내에서 자가 치유(자동 재시작)되고 오작동이 모니터링되기를 원합니다.

**Why this priority**: 리소스 한도를 설정하지 않으면 하나의 컨테이너 오작동이 물리 호스트 컴퓨터 전체를 다운시켜 전체 서비스 불능을 야기하므로 가장 핵심적인 가용성 요구사항입니다.

**Independent Test**: 특정 컨테이너에 스트레스 도구(Stress tool) 등을 통해 CPU/메모리 부하를 인위적으로 주었을 때, 설정된 임계치 한도 내로 자원 점유율이 억제되고 호스트의 다른 컨테이너 및 코어 프로세스가 정상 가동 상태를 유지하는지 모니터링하여 테스트합니다.

**Acceptance Scenarios**:

1. **Given** 프로덕션 도커 컴포즈 서비스가 실행 중인 상태에서, **When** 백엔드 API 서비스에 과도한 메모리 사용이 발생하여 한계점에 도달했을 때, **Then** 해당 컨테이너만 메모리 OOM(Out of Memory)으로 리스타트되며 호스트의 다른 컨테이너(DB, Redis 등)는 영향을 받지 않고 계속 기동 상태를 유지한다.
2. **Given** 특정 서비스에 대해 헬스 체크가 설정된 상태에서, **When** 해당 서비스 내부 프로세스가 교착 상태(Deadlock)에 빠져 헬스 체크 실패 기준을 초과할 때, **Then** 도커 데몬이 이를 `unhealthy` 상태로 감지하고 컴포즈에 지정된 리스타트 정책에 따라 정상 상태로 복구하기 위해 컨테이너를 재시작한다.

---

### User Story 2 - 비인가 접근을 차단하는 호스트 포트 보안 (Priority: P1)

보안 위협으로부터 데이터베이스(PostgreSQL), 캐시(Redis) 및 내부 백엔드 서버(API, Celery)를 보호하기 위해, 인터넷망(Public IP)으로부터의 비인가 직접 접근을 완전히 격리하고 오직 공인 게이트웨이(Nginx Reverse Proxy 등)를 통한 트래픽만 내부 가상 네트워크망을 거쳐 인입될 수 있도록 통제하기를 원합니다.

**Why this priority**: 데이터베이스나 캐시의 포트가 외부에 노출되면 크리덴셜 탈취 및 무작위 대입 공격의 타겟이 되어 데이터 유실 또는 인프라 훼손의 직접적인 원인이 되므로 최상위 우선순위의 보안 요건입니다.

**Independent Test**: 서비스가 구동 중인 프로덕션 호스트의 공인 IP를 대상으로 포트 스캔을 수행하여 HTTP/HTTPS 포트 외의 내부 컴포넌트 포트들(5432, 6379, 8000 등)이 외부에서 접근 불가(Closed/Filtered) 상태로 차단되어 있는지 검증합니다.

**Acceptance Scenarios**:

1. **Given** 전체 프로덕션 도커 컴포즈가 호스트 기기에서 가동 중인 상황에서, **When** 외부 호스트에서 이 서버의 공인 IP와 DB 포트(5432) 또는 Redis 포트(6379)로 TCP 연결을 시도할 때, **Then** 해당 포트 접속 요청은 타임아웃 혹은 거부(Connection Refused)되어 직접 접속이 전면 차단된다.
2. **Given** 컴포즈로 격리된 네트워크 환경 내부에서, **When** API 컨테이너가 로컬 호스트명(예: `db`, `redis`)을 통해 내부 포트로 통신을 시도할 때, **Then** 도커 브리지 네트워크를 통해 라우팅되어 자격 증명 검증을 거친 후 정상적으로 연결 및 쿼리가 수행된다.

### User Story 3 - 프로덕션 로그 로테이션 및 디스크 고갈 예방 (Priority: P2)

운영 중에 생성되는 도커 컨테이너들의 로그가 물리 디스크 공간을 무제한으로 무단 점유하여 호스트 시스템의 디스크 풀(Disk Full) 장애를 일으키지 않도록, 모든 로그 파일의 크기가 일정 규격 내로 제한되고 안전하게 로테이션 관리되기를 원합니다.

**Why this priority**: 도커의 기본 로그 드라이버는 제한 없이 파일이 무한 증식하므로, 장기 운영 시 디스크 용량 고갈로 인한 전체 서버 다운을 사전 방어하기 위한 운영 안정성 요건입니다.

**Independent Test**: 컨테이너의 표준 출력(Stdout)으로 지속적인 대량 로그를 임의 발생시키고, 호스트 상의 해당 컨테이너 로그 디렉토리를 모니터링하여 단일 파일 용량이 최대 설정치에 도달했을 때 새 파일로 분할(Rotation)되고 총 보존 개수를 넘어선 구형 로그가 정상 파지(Purge)되는지 확인합니다.

**Acceptance Scenarios**:

1. **Given** 로그 로테이션 정책이 강제 적용된 프로덕션 컨테이너 환경에서, **When** 백엔드 컨테이너가 지속적으로 디버그성 다량 로그를 출력하여 설정된 한계 용량(예: 10MB)에 도달할 때, **Then** 기존 로그는 분할 보관 처리되고 새로운 활성 로그 파일이 생성되며 전체 누적 보존 개수(예: 3개)를 넘어선 가장 오래된 로그 파일은 디스크에서 자동 삭제된다.

---

### Edge Cases

- **리소스 과제한으로 인한 OOM 킬러 크래시 발생**: 컨테이너가 할당된 메모리 임계 한도를 넘어서 커널/도커에 의해 OOM Kill을 당할 때, 해당 서비스의 재구동으로 인한 연속성 붕괴 및 데이터베이스의 경우 트랜잭션 롤백 안정성이 유지될 수 있는 컴포즈 리스타트 정책의 백오프 한계가 유효하게 작동하는가?
- **호스트 포트의 안전한 우회 접근(SSH 터널링 등) 지원 여부**: 개발자 또는 DB 관리자가 인프라 관리 및 긴급 쿼리 수행을 위해 DB에 접근해야 할 때, 공인 IP 포트 노출 없이 호스트 내부 포트 바인딩(`127.0.0.1:5432`) 또는 SSH 포트 포워딩을 경유한 물리적인 보안 연결망이 유효하게 확보되는가?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 프로덕션 환경의 모든 개별 컨테이너(API Server, Celery Worker, PostgreSQL, Redis 등)에 대한 CPU 점유율 임계 설정 및 메모리 예약/최대 한도(Resource Limits & Reservations)를 독립적으로 정의하고 격리해야 한다.
- **FR-002**: 외부 인터넷망(Public IP)으로부터 유입되는 비인가 트래픽이 데이터베이스 및 캐시와 같은 백단 보조 컴포넌트의 호스트 포트에 직접 도달하지 못하도록 차단해야 하며, 오직 웹 서비스 포트(HTTP 80, HTTPS 443)만 호스트 공인 IP로 노출하고 나머지 모든 포트(모니터링 툴 등 포함)는 호스트 외부 노출을 전면 차단하고 내부 격리된 도커 네트워크망 내에 위치시켜야 한다.
- **FR-003**: 오직 역방향 프록시(Nginx 등) 웹 게이트웨이 컴포넌트만 외부로 노출되어 퍼블릭 포트(80 및 443)와 바인딩되어야 하며, 이를 통해 들어온 트래픽을 도커 격리 브리지 네트워크 내부의 `api-server` 서비스로 위임하여 중계해야 한다.
- **FR-004**: 컨테이너의 영속적인 실 데이터 저장을 위해 도커 관리형 볼륨(Docker Named Volume)을 사용하여 인프라 간 이식성을 확보하고 호스트와 컨테이너 간의 UID/GID 파일 권한 불일치 에러를 원천 방어해야 한다.
- **FR-005**: 모든 프로덕션용 컨테이너에 대해 CPU 및 메모리 점유율을 튜닝하는 설정값을 세분화해야 하며, 프로덕션 환경의 개별 컨테이너(API, Celery, DB) 자원 격리 임계값은 도커 컴포즈 파일에 고정된 절대 용량(limits 및 reservations)으로 선언하여 오작동 및 누락을 방어해야 한다.
- **FR-006**: 각 컨테이너 서비스에 상태 감지를 위한 명시적 헬스 체크(Healthcheck) 명령 및 인터벌, 타임아웃, 재시도 횟수를 선언하여 비정상 컨테이너의 격리와 자동 재시작을 지원해야 한다.
- **FR-007**: 도커 데몬 및 개별 컴포즈 서비스 레이어에 로그 드라이버 속성(json-file)을 적용하여 로그 파일당 크기 한도(Max Size) 및 보존 파일 개수(Max File)를 강제함으로써 디스크 점유 용량이 임계치를 초과하지 않도록 통제해야 한다.
- **FR-008**: 데이터베이스 패스워드, 외부 API 키, 암호화 키 등 보안에 민감한 정보는 프로덕션 YAML에 절대 하드코딩하지 않고 외부 환경 설정 파일(`.env.prod`)로부터 안전하게 수급 및 격리 주입받아야 한다.

### Key Entities *(include if feature involves data)*

- **Container Resource Specification**: 각 도커 컨테이너 서비스에 배분될 리소스(CPU 한도 및 점유 가중치, 메모리 물리 한도 및 예약 크기)의 정합성을 담은 사양 엔티티.
- **Network Access Binding Control**: 호스트와 내부 컨테이너 포트 간의 연결 속성. 공인 IP 바인딩, 루프백 IP(`127.0.0.1`) 바인딩, 포트 노출 없음(Internal Only Network) 정책을 분류 관리.
- **Log Rotation Config**: 로그 파일 크기 제한 및 백업 로테이션 주기 등을 정의한 설정 속성 엔티티.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 호스트 서버의 Public IP를 대상으로 포트 스캔을 수행했을 때, 승인된 포트(예: HTTP 80, HTTPS 443)를 제외한 데이터베이스(5432), 캐시(6379), 백엔드 API(8000) 등 나머지 모든 포트의 직접 접근 시도가 100% 차단되거나 Filtered 상태여야 한다.
- **SC-002**: 임의로 헬스 체크 경로의 결과값을 비정상(500 에러 또는 응답 없음)으로 변환시켰을 때, 지정된 헬스 체크 주기 및 재시도(예: 3회 실패) 후에 도커 엔진이 60초 이내에 이를 감지하고 컨테이너를 자동으로 정상 재가동 시켜야 한다.
- **SC-003**: 백엔드 또는 비동기 워커 서비스에 과부하 상황이 발생하더라도 해당 서비스 컨테이너의 물리적 CPU 할당량 및 메모리 사용은 정밀하게 격리되어, 동일 호스트 내 데이터베이스 컨테이너의 메모리 점유 및 디스크 I/O 자원을 방해하지 않고 보장하여야 한다.
- **SC-004**: 아무리 많은 로깅 트래픽이 발생하여도 단일 서비스 컨테이너당 적재되는 최대 디스크 로그 용량은 합계 30MB(10MB x 3개)를 절대 초과하지 않아야 한다.

## Assumptions

- 프로덕션 대상 호스트 OS의 방화벽 설정(예: iptables, firewalld, UFW 등)과 도커 브리지 네트워크의 패킷 포워딩 정책 간에 충돌이 없도록 사전 구성이 검증되었음을 전제한다.
- 데이터베이스 컨테이너의 볼륨 마운트는 유실을 원천 방지하기 위해 컨테이너 삭제/재성성 사이클과 별도로 유지되는 안전한 볼륨 인프라를 사용한다.
- 프로덕션 배포에 필요한 민감 설정은 로컬 개발 환경과 명확하게 물리 분리된 환경 변수 파일로부터 런타임에 동적으로 바인딩된다.
- CPU 및 메모리 제한은 프로덕션 호스트의 물리 하드웨어 사양(예: 8 vCPU, 16GB RAM 등)에 과부하를 주지 않는 범위 내로 배분하여 설정된다.
