# Research & Technology Decisions: 소비 시각화 차트 및 예산 게이지 (가계부 UI 고도화 1단계)

본 문서는 가계부 UI 고도화 1단계를 구현하기 위해 필요한 기술적 결정 사항, 차트 시각화 라이브러리 분석 및 성능 최적화(100ms 이내 쿼리 응답 시간 보장) 방안에 대한 연구 내용을 담고 있습니다.

## 1. 프론트엔드 차트 시각화 라이브러리 선정

### 비교 분석

| 라이브러리 | 장점 | 단점 | 선택 여부 |
|:---|:---|:---|:---:|
| **Chart.js** (`vue-chartjs` 결합) | - 캔버스(Canvas) 기반의 매우 뛰어난 성능<br>- Vue 3 공식 호환 래퍼 제공으로 리액티브 바인딩 용이<br>- 번들 사이즈가 상대적으로 가볍고 풍부한 커뮤니티 예제 존재 | - SVG가 아닌 Canvas 방식이므로 해상도 변화 시 픽셀 깨짐 주의 필요 (반응형 설정 필수) | **선택 (Recommended)** |
| **ApexCharts** (`vue3-apexcharts`) | - 미려한 그라데이션 및 풍부한 기본 애니메이션 효과<br>- SVG 기반으로 해상도에 구애받지 않음 | - 번들 사이즈가 매우 크며, 단순 대시보드 시각화 용도로는 오버헤드가 큼 | 기각 |
| **Frappe Charts** | - 의존성이 없고 번들이 극도로 가벼움<br>- 깔끔한 미니멀 디자인 | - Vue 3와 반응형 데이터 바인딩 시 복잡한 Lifecycle 이벤트 수동 제어 필요 | 기각 |

### 결정사항 (Decision)
* **선택**: **`Chart.js` (v4+) & `vue-chartjs` (v5+)**
* **이유**: Vue 3의 컴포지션 API와 반응형 상태(`ref`, `reactive`)에 맞춰 차트 데이터가 자연스럽게 동기화(Re-render)되며, 모바일 PWA 환경에서 시스템 리소스 점유율을 줄이기 위해 가볍고 캔버스 렌더링 속도가 빠른 `Chart.js`가 최적입니다. 헌법 5조(Mobile-first PWA) 및 반응형 웹 그리드 요건을 만족하기 위해 가변 가로폭(`responsive: true`) 설정을 활성화하여 반응형 디자인을 완벽히 충족합니다.

## 2. API 설계 및 지출 데이터 실시간 집계 최적화 (100ms 방어)

### 비교 분석

| 집계 아키텍처 | 장점 | 단점 | 선택 여부 |
|:---|:---|:---|:---:|
| **클라이언트 측 전수 집계** | - 백엔드 개발 복잡성 없음<br>- 기존 Ledger API 그대로 활용 가능 | - 데이터 전송량이 무겁고(오버헤드), 로드 속도가 느려 1.5초 성공 기준(SC-001) 만족 불가 | 기각 |
| **서버 실시간 raw 집계** (매 쿼리 호출) | - 항상 최신의 100% 실시간 데이터 정합성 보장 | - 데이터가 늘어남에 따라 DB Group By 연산 부하 증가로 100ms 이내 응답 방어(Phase 2 게이트) 실패 위험 | 기각 |
| **하이브리드 캐싱 집계** (To-be) | - 당월은 실시간 집계하고, 과거 월은 Redis/DB 캐시 테이블을 조회하여 100ms 이내 초고속 반환 | - 가계부 내역의 CRUD 발생 시 당월 캐시 및 통계 집계 상태를 무효화(Invalidation)하는 동기화 로직 필요 | **선택 (Recommended)** |

### 결정사항 (Decision)
* **선택**: **하이브리드 캐싱 집계 전략 및 전용 대시보드 API 엔드포인트 `/api/ledgers/dashboard/` 신설**
* **이유**:
  * 카테고리별 원형 차트, 월별 지출 막대 차트, TOP 3 가맹점, 월 예산 게이지 등의 정보는 개별 API로 쪼개어 호출하기보다, 하나의 DTO로 가공하여 단 한 번의 HTTP 요청으로 렌더링하는 것이 PWA 모바일 성능 향상(SC-001)에 핵심적입니다.
  * 데이터베이스 인덱스를 `(user_id, transaction_date)`로 최적화하고, 가계부의 CRUD가 발생할 때만 현재 월의 통계 캐시 데이터를 갱신(Cache Invalidation)하고, 과거 월(3개월, 6개월, 12개월 등) 데이터는 변경되지 않으므로 캐시 데이터를 반환하여 쿼리 응답 시간을 상시 **100ms 이내**로 완벽하게 통제합니다.

## 3. 예산 관리 및 영속화 아키텍처

### 비교 분석

| 아키텍처 안 | 장점 | 단점 | 선택 여부 |
|:---|:---|:---|:---:|
| **프론트엔드 로컬 스토리지 임시 보존** | - 백엔드 DB 설계 수정 필요 없음 | - 기기 간 예산 동기화 불가, 영구 보존 안 됨 | 기각 |
| **`User` 모델 내 `monthly_budget` 필드 추가** | - 단순 유저 정보의 연장으로 관리 용이 | - 월별 예산 이력(예: 1월 예산, 2월 예산 등)을 관리하기 어려움 | 기각 |
| **`MonthlyBudget` 독립 모델 설계** (To-be) | - 사용자별, 특정 연월(`YYYY-MM`)별 예산 금액을 독립 이력으로 적재 가능 | - 모델 및 마이그레이션 신설 필요 | **선택 (Recommended)** |

### 결정사항 (Decision)
* **선택**: **`MonthlyBudget` 독립 Django 모델 구축**
* **이유**: 사용자는 월별로 다른 지출 목표를 세울 수 있어야 하므로, `user_id`와 `budget_month` (Date/String 형식, 예: `2026-06`)를 복합 유니크 키로 가지는 예산 테이블을 신설합니다. 이를 통해 대시보드에서 예산 편집 버튼을 통해 API `/api/budgets/`를 호출하여 특정 월의 예산을 동적으로 즉시 저장 및 실시간 게이지에 바인딩할 수 있도록 처리합니다.
