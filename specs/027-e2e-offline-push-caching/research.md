# Research & Architectural Decisions: E2E Offline Push & Caching

이 문서는 오프라인 웹 푸시 알림 도달 및 디바이스 캐싱 데이터 무결성 검증 피처와 관련된 핵심 비즈니스 및 아키텍처 의사결정 사항을 보관합니다.

---

## 1. 오프라인 누적 알림 로컬 IndexedDB 보존 정책

### 결정사항 (Decision)
- **최신 100개 & 30일 이내 알림만 IndexedDB에 캐시 보존 및 초과분 자동 퍼지 (Option A)**

### 타당성 (Rationale)
- **백엔드 라이프사이클과의 동등성**: 백엔드 `NotificationLog` 데이터가 Celery Beat를 통해 30일 주기로 자동 정리되므로, 클라이언트 로컬 캐시도 이 수명 주기(TTL)에 동기화하여 데이터 무결성을 이루는 것이 가장 아키텍처적으로 직관적입니다.
- **성능 및 스토리지 보호**: 기기 자원 보호 및 브라우저 IndexedDB 쿼터 한계 초과를 사전에 방어하며, 대량 알림 적재 시 발생할 수 있는 목록 조회/렌더링 지연 현상을 원천적으로 차단합니다.

### 고려된 대안 (Alternatives considered)
- **Option B (용량 한도 내 제한 없음 & 브라우저 자동 퍼지)**: 브라우저가 스토리지 용량 한계 도달 시 임의로 IndexedDB 전체 데이터를 일괄 퍼지하므로, 사용자가 과거 일부 유효한 알림을 강제로 상실하게 되어 예측 불가능한 사용자 경험(UX)을 유발하므로 기각했습니다.
- **Option C (로컬 보존 없음 & 온라인 복귀 시 항상 백엔드 API 재조회)**: 오프라인 상황에서 사용자가 가계부 앱의 알림 목록 탭에 진입했을 때 기존 내역을 아예 조회할 수 없어 PWA의 오프라인 가동 능력이 상실되므로 기각했습니다.

## 2. 백엔드와 로컬 캐시 상태의 불일치 보정 동기화 시점

### 결정사항 (Decision)
- **앱 포그라운드 활성화(Document Focus 진입) 시 즉시 1회 자동 동기화 (Option A)**

### 타당성 (Rationale)
- **UX 최적화**: 사용자가 PC 등 다른 단말에서 알림을 읽고 모바일 화면을 켰을 때(Focus 진입), 즉시 1회 동기화가 트리거되므로 상태 지연 없이 정합성 불일치를 즉각 해결할 수 있습니다.
- **네트워크/서버 부하 최소화**: 지속적으로 백그라운드 폴링을 수행하지 않고, 사용자가 실제로 화면을 활성화했을 때만 API를 호출하므로 API 호출 빈도와 전력 소모를 최적으로 절감합니다.

### 고려된 대안 (Alternatives considered)
- **Option B (수동 새로고침 시에만 동기화)**: 사용자가 앱 내 새로고침 아이콘을 직접 누르기 전까지는 타 기기에서 처리된 읽음 상태가 업데이트되지 않아 UX 혼란을 가중시키므로 기각했습니다.
- **Option C (주기적 백그라운드 폴링 - 예: 15분)**: iOS Safari 등 모바일 PWA 제약 조건 상 백그라운드에서 타이머나 Background Sync가 완벽히 보장되기 어렵고, 백엔드 서버에 불필요한 지속 트래픽 부하를 유발하므로 기각했습니다.

## 3. 오프라인 E2E 무결성을 보장하기 위한 테스트 자동화 도구 및 검증 파이프라인 수립 범위

### 결정사항 (Decision)
- **Playwright 오프라인 에뮬레이션 모드 E2E 테스트 자동화 구축 및 CI 통합 (Option A)**

### 타당성 (Rationale)
- **기계적 하네스 수호**: 브라우저 오프라인 에뮬레이션(`context.setOffline(true)`), 서비스 워커 등록, IndexedDB 캐싱, 그리고 백엔드 API 연동을 유기적으로 검증할 수 있는 신뢰성 높은 기계적 통합 검증 환경(Playwright)을 확보합니다.
- **회귀 테스트 방지**: 향후 sw.js 등의 리팩토링 발생 시 오프라인 정합성이 깨지는 버그를 CI 상에서 자동으로 사전 탐지 및 차단할 수 있습니다.

### 고려된 대안 (Alternatives considered)
- **Option B (로컬 개발용 모의 수동 시나리오 검증 및 확인)**: 매 배포 및 커밋 시마다 브라우저에서 네트워크 선을 뽑고 수동으로 DB 조회를 대조하는 오버헤드가 막대하여 장기적으로 테스트가 누락될 리스크가 크므로 기각했습니다.
- **Option C (Django 유닛 테스트 목업 테스트로 한정)**: 백엔드의 Acknowledgment 비즈니스 로직 단위 테스트는 가능하나, 실제로 오프라인 상태에서 서비스 워커가 이벤트를 가로채 IndexedDB에 적재하는 프론트엔드 E2E 레이어의 무결성은 증명할 수 없으므로 기각했습니다.
