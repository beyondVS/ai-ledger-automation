# Feature Specification: Database Integrity & Payment Duplicate Prevention & Category UI Fix

**Feature Branch**: `017-db-integrity-payment-fix`

**Created**: 2026-06-11

**Status**: Approved

**Input**: User description: "데이터베이스 무결성 보장을 위한 예외 처리 및 롤백 가이드라인 고도화. Django ORM 트랜잭션 블록(transaction.atomic())을 엄밀히 통제하여 마스터 적재 실패 시 품목 리스트까지 롤백하고, 중복 결제 인입 시 무시(Django ORM get_or_create 혹은 bulk_create ignore_conflicts 옵션 활용)하는 안정성 적용. **[추가 계획] 동일 상품 연속 결제 시 오탐지 방지를 위한 중복 체크 알고리즘 고도화 (결제 승인번호/거래 시간 연동 등). 프론트엔드 수정 내역 모달(FE-05-B) 내 카테고리 셀렉트박스 데이터 매핑 누수 버그 해결.**"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 원자적 결제 데이터 적재 및 중복 유입 방지 (Priority: P1)

영수증이나 결제 건이 시스템에 기록될 때 마스터 정보(가계부 마스터)와 품목 상세 정보(각 결제 항목들)가 모두 완벽히 기록되거나, 오류 시 완전히 취소되어 파편화된 데이터가 남지 않아야 합니다. 또한 시스템 결함으로 동일한 결제 요청이 짧은 시간 내에 여러 번 유입될 경우, 중복 데이터가 계속 쌓이지 않고 안정적으로 우회 처리되어야 합니다.

**Why this priority**: 결제 데이터는 가계부의 핵심 데이터이며 신뢰성이 최우선입니다. 데이터 파편화나 무의미한 중복 데이터 축적을 방지하는 것은 데이터 무결성을 위해 가장 시급한 요구사항입니다.

**Independent Test**: 마스터 적재 성공 후 품목 적재 중 인위적인 데이터 오류를 발생시켜 트랜잭션이 전체 롤백(롤백 후 데이터베이스에 마스터 레코드와 품목 레코드가 둘 다 남아있지 않음)되는지 확인하고, 동일한 결제 정보를 연속으로 2회 보냈을 때 두 번째 요청에서 데이터베이스 에러 없이 정상 응답을 받으며 단 하나의 유일한 결제 레코드만 존재함을 검증합니다.

**Acceptance Scenarios**:

1. **Given** 가계부 적재를 위한 유효한 마스터 데이터와 품목 상세 리스트가 주어졌을 때, **When** 적재 과정 중 품목 중 일부가 잘못된 데이터(예: 길이 초과, 필수 필드 누락 등)로 인해 저장이 실패하면, **Then** 앞서 성공적으로 임시 적재되었던 마스터 데이터를 포함하여 전체 결제 트랜잭션이 데이터베이스에서 흔적 없이 취소(Rollback)되어야 합니다.
2. **Given** 이미 시스템에 성공적으로 기록된 결제 건이 존재할 때, **When** 동일한 결제 건이 네트워크 지연 등의 이유로 다시 중복 인입되면, **Then** 시스템은 기존 결제를 중복 생성하여 에러를 내거나 데이터를 복제하는 대신, 요청을 정상 처리된 것으로 간주하고 기존 데이터의 무결성을 그대로 유지(중복 요청 무시 및 바이패스)해야 합니다.

### User Story 2 - 동일 상품 연속 결제 오탐지 방지 (Priority: P2)

사용자가 마트 등에서 동일한 상품을 의도적으로 연달아 구매하거나, 동일한 금액을 연속으로 결제한 경우 이를 오작동으로 인한 중복 결제로 오해하여 데이터를 누락하지 않고 구분해내야 합니다.

**Why this priority**: 실제 정상적인 연속 거래를 시스템이 임의로 차단하거나 생략하면 가계부 누락이 발생하여 사용자 경험이 손상됩니다.

**Independent Test**: 동일한 상점과 동일한 금액의 결제 요청이 수 분 내에 연속으로 유입되더라도, 거래 승인 번호가 다르거나 거래 상세 시각이 다를 때 각각 개별 결제 건으로 올바르게 분리 적재되는지 검증합니다.

**Acceptance Scenarios**:

1. **Given** 사용자가 같은 상점에서 동일 금액의 상품을 연속으로 구매하여 다수의 결제 요청이 발생했을 때, **When** 결제 승인번호가 서로 다르게 매핑되어 인입되거나 일정한 허용 시간 차를 두고 유입되면, **Then** 시스템은 이를 중복 결제 오류로 간주하여 무시하지 않고 각각 독립된 개별 거래 건으로 모두 안전하게 적재해야 합니다. (단, 거래 승인번호가 다르면 무조건 개별 거래로 인정하며 승인번호가 없거나 동일할 때는 1분(60초) 이내의 동일 가맹점/동일 금액 거래만 중복으로 처리합니다.)

### User Story 3 - 수정 내역 모달(FE-05-B) 내 카테고리 누수 버그 해결 (Priority: P3)

사용자가 수정 내역 모달 창을 열었을 때, 결제 건에 이미 할당되어 있는 카테고리 정보가 드롭다운 셀렉트박스에 정확히 매핑되어 보여야 하며, 카테고리를 변경하고 저장할 때 이 매핑 데이터가 유실되지 않고 안전하게 업데이트되어야 합니다.

**Why this priority**: 사용자가 수정 화면을 볼 때 할당된 카테고리가 비어 보이거나 유실되는 버그는 직접적인 UI/UX 만족도를 저하시키고 데이터 혼선을 초래합니다.

**Independent Test**: 카테고리가 '식비'로 지정된 거래 내역에 대해 수정 모달(`FE-05-B`)을 열었을 때 셀렉트박스의 초기값이 '식비'로 올바르게 선택되어 있는지 확인하고, 이를 '교통비'로 변경한 후 저장했을 때 원본 데이터가 '교통비'로 바르게 수정 반영되는지 테스트합니다.

**Acceptance Scenarios**:

1. **Given** 카테고리가 이미 지정된 거래 내역 데이터가 로드되어 있을 때, **When** 수정 내역 모달(`FE-05-B`)을 활성화하면, **Then** 카테고리 셀렉트박스에는 해당 거래의 기존 카테고리 값이 정확히 매핑 및 렌더링되어 표시되어야 합니다. (만약 기존 지정 카테고리가 없거나 백엔드 매핑이 유실된 경우에는 '미분류'를 기본 선택 상태로 보여줍니다.)
2. **Given** 사용자가 수정 모달에서 카테고리를 다른 값으로 수정한 상태에서, **When** 저장 버튼을 눌러 제출을 완료하면, **Then** 데이터 바인딩이 누수 없이 정상적으로 갱신되어 리스트 및 상세 화면에 변경된 카테고리가 즉시 반영되어야 합니다.

---

### Edge Cases

- **네트워크 지연으로 인한 극히 짧은 간격(예: 0.1초 미만)의 물리적 중복 요청:** 동일 결제 건에 대해 여러 서버 프로세스가 거의 동시에 데이터베이스 쓰기를 시도할 때 발생할 수 있는 데드락이나 고유 제약 조건 위반(Unique Constraint Violation)을 안전하게 회피해야 합니다.
- **승인 번호가 누락된 수동 결제 건의 연속 입력:** 신용카드 자동 결제 알림이 아닌, 사용자가 직접 수동으로 동일 내역을 연속 기재하는 경우 승인번호가 없더라도 거래 시각과 내용을 조합하여 적절하게 중복을 필터링해야 합니다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 결제 마스터 레코드와 하위 품목 리스트를 저장할 때 데이터의 원자성(Atomicity)을 보장해야 합니다. 어느 하나라도 실패하면 모두 취소(Rollback)되어야 합니다.
- **FR-002**: 동일한 고유 ID(승인 식별값 등)를 가진 중복 결제 데이터가 인입되었을 때, 데이터베이스 충돌 오류를 발생시키지 않고 충돌을 안전하게 무시하며 기존 상태를 보존할 수 있어야 합니다.
- **FR-003**: 동일 금액/가맹점 조건의 연속 결제에 대해, 승인번호나 정밀한 거래 시각을 대조하여 실제 중복 유입과 사용자의 의도적 연속 결제를 정밀하게 분별하는 중복 판단 알고리즘을 수행해야 합니다.
- **FR-004**: 수정 내역 모달(`FE-05-B`) 컴포넌트는 거래 데이터 로드 시 기존 카테고리 고유값을 누락 없이 바인딩하여 드롭다운 선택 상태에 매핑해야 합니다.
- **FR-005**: 사용자가 카테고리를 변경하고 제출할 때, 폼 데이터 바인딩 오류나 상태 누수로 인해 업데이트 요청 시 카테고리 ID 필드가 유실되는 현상을 완벽히 방어해야 합니다.

### Key Entities *(include if feature involves data)*

- **결제 마스터 (Ledger)**: 가계부 내역의 핵심 부모 레코드. 결제 총액, 결제 수단, 거래 일시, 가맹점 정보, 결제 승인번호 등을 포함합니다.
- **결제 품목 (Ledger Item)**: 결제 마스터에 종속된 개별 세부 품목. 품목명, 단가, 수량, 카테고리 정보 등을 담으며, 마스터가 삭제되거나 적재 실패 시 원자적으로 함께 롤백/삭제되어야 합니다.
- **카테고리 (Category)**: 결제 품목 또는 결제 마스터에 매핑되는 분류 코드. 프론트엔드 UI 수정 폼에서 드롭다운 옵션으로 맵핑 및 표시됩니다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 인위적인 품목 오류 테스트 시, 부모 마스터 레코드가 100% 잔존하지 않고 함께 롤백되는 원자성 정합성을 달성해야 합니다.
- **SC-002**: 동시성 결제 중복 인입 테스트 시, 중복 에러가 발생하지 않으며 단 1건의 결제 레코드만 유지되는 성공률 100%를 보장해야 합니다.
- **SC-003**: 동일 금액/동일 가맹점 연속 결제 시나리오에서 오탐지로 누락되는 개별 정상 결제 건의 비율을 0%로 통제해야 합니다.
- **SC-004**: 수정 내역 모달(`FE-05-B`)을 100회 실행 시 카테고리 드롭다운의 기존 지정 데이터 바인딩 성공률 100%를 보여야 합니다.

## Assumptions

- 결제 정보 인입 시 가맹점에서 발행하는 고유 결제 승인 번호(Approval Number)가 제공되거나, 미제공 시 이를 대신할 식별자(UUID 또는 거래 시각의 조합)가 보장됩니다.
- 모달(`FE-05-B`) 내 카테고리 목록 데이터는 사전에 컴포넌트가 활성화될 때 스토어나 부모 컴포넌트로부터 정상적으로 주입되거나 API를 통해 무결하게 조회됩니다.
