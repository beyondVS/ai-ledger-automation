## Clarifications

### Session 2026-06-18

- Q: v1에서 알림 발송 트리거 대상 이벤트 범위 및 월별 지출 경보의 발동 기준은? → A: 영수증 처리 완료 + 월별 예산 임계 초과(기본값 80%) 2종으로 확정. 가계부 수동 수정 저장 이벤트는 v2 백로그로 이관.
- Q: 월별 예산 임계값(80%)을 사용자가 직접 설정·변경할 수 있어야 하나요? → A: 시스템 전체 고정값 80%로 단순화. 운영자가 환경 설정(서버 설정값)으로만 변경 가능하며, 사용자 개별 설정 UI는 이번 범위에서 제외한다.
- Q: 알림 구독 On/Off 토글 UI를 어디에 배치할까요? → A: 기존 사용자 프로필/설정 페이지 내 섹션으로 통합 배치. 신규 페이지 생성 없이 기존 레이아웃 재사용.
- Q: FCM 서비스 계정 자격증명을 어떤 방식으로 주입할까요? → A: 서비스 계정 JSON 전체 내용을 단일 환경 변수(GOOGLE_APPLICATION_CREDENTIALS_JSON)에 문자열로 주입. 파일 마운트 방식 미사용, 기존 .env 보안 정솥 준수.
- Q: 알림 발송 이력의 보존 기간 및 조회 주체는 어떻게 설정할까요? → A: 30일 보존 + 운영자 전용 어드민 조회. 주기적 자동 정리 잡(cleanup job)으로 30일 초과 이력 삭제, 최종 사용자 직접 조회 미제공.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 웹 푸시 알림 구독 및 수신 (Priority: P1)

서비스를 사용하는 최종 사용자가 브라우저에서 푸시 알림 수신에 동의하면, 시스템은 해당 기기의 구독 정보를 안전하게 저장하고 이후 중요한 가계부 이벤트(예: 영수증 처리 완료, 월별 지출 경보 등)가 발생할 때 해당 사용자의 기기로 실시간 알림을 발송한다.

**Why this priority**: 사용자가 알림을 받으려면 구독이 먼저 성립되어야 하며, 이 흐름이 전체 파이프라인의 진입점이므로 P1로 설정한다.

**Independent Test**: 사용자가 브라우저 알림 허용 후 구독 엔드포인트가 저장되는지 확인하고, 이후 테스트 알림 발송 시 브라우저에 알림이 도달하면 단독 검증 완료.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자가 알림 허용을 클릭했을 때, **When** 브라우저가 구독 정보를 생성하면, **Then** 시스템은 해당 구독을 사용자 계정에 등록하고 성공 응답을 반환한다.
2. **Given** 등록된 구독이 있는 사용자에게 이벤트가 발생했을 때, **When** 시스템이 알림 발송 요청을 큐에 적재하면, **Then** 해당 사용자의 브라우저 또는 기기에서 푸시 알림이 도달한다.
3. **Given** 사용자가 알림 수신을 거부했을 때, **When** 시스템이 발송을 시도하면, **Then** 발송을 생략하고 해당 구독을 비활성 상태로 표시한다.

---

### User Story 2 - 비동기 백그라운드 큐를 통한 알림 발송 (Priority: P2)

영수증 파싱 완료, 월별 예산 임계 초과(기본값: 80%) 등 시스템 내부에서 특정 이벤트가 발생할 때, 알림 발송 로직이 메인 요청 흐름을 차단하지 않고 독립된 백그라운드 큐를 통해 비동기적으로 처리된다. 발송 실패 시 자동 재시도가 수행된다.

**Why this priority**: 알림 발송이 동기 요청을 차단하면 사용자 경험과 API 응답성이 저하되므로, 비동기 큐 분리는 신뢰성 있는 알림 서비스의 핵심 요소이다.

**Independent Test**: 영수증 파싱 API 완료 후 알림 발송 태스크가 큐에 삽입되고, 최종적으로 실제 기기에 알림이 도달하는 전 과정을 독립 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 시스템 이벤트(영수증 처리 완료 등)가 발생했을 때, **When** 알림 발송 요청이 생성되면, **Then** 메인 비즈니스 로직 처리는 즉시 완료되고 알림 발송은 별도 큐를 통해 독립적으로 처리된다.
2. **Given** 큐에 적재된 알림 발송 작업이 실행될 때, **When** 외부 푸시 서비스(FCM 또는 APNs)가 일시적 오류를 반환하면, **Then** 지수 백오프(Exponential Backoff) 정책에 따라 최대 3회까지 자동 재시도를 수행한다.
3. **Given** 최대 재시도 횟수를 초과한 발송 실패가 발생했을 때, **When** 더 이상 재시도가 불가능하면, **Then** 해당 발송 이력을 실패 상태로 영속화하고 시스템 로그에 기록한다.

---

### User Story 3 - FCM / APNs 이중 채널 발송 라우팅 (Priority: P2)

구독자의 기기 유형(Android/Chrome은 FCM, iOS/Safari는 APNs)에 따라 동일한 알림 페이로드가 적절한 외부 푸시 채널로 자동 라우팅되어 발송된다. 발송 모듈은 VAPID V2 표준을 준수하여 각 채널에 서명된 요청을 전송한다.

**Why this priority**: VAPID V2 + FCM/APNs 이중 지원은 특정 플랫폼에서 알림이 누락되는 현상을 방지하는 필수 커버리지이다.

**Independent Test**: Android Chrome과 iOS Safari 각각에 테스트 알림을 발송하여 양측 모두 정상 수신되면 독립 검증 완료.

**Acceptance Scenarios**:

1. **Given** Chrome/Android 브라우저가 등록한 구독 엔드포인트에 알림을 발송할 때, **When** 발송 모듈이 라우팅을 판단하면, **Then** FCM HTTP v1 API를 통해 VAPID 서명된 요청을 전송한다.
2. **Given** Safari/iOS 디바이스가 등록한 구독 엔드포인트에 알림을 발송할 때, **When** 발송 모듈이 라우팅을 판단하면, **Then** APNs HTTP/2 채널을 통해 VAPID 서명된 요청을 전송한다.
3. **Given** 알림이 성공적으로 발송되었을 때, **When** 외부 서비스가 성공 응답을 반환하면, **Then** 해당 발송 이력을 성공 상태로 기록한다.

---

### User Story 4 - 구독 만료 및 자동 정리 (Priority: P3)

외부 푸시 서비스로부터 구독이 만료되었거나 유효하지 않다는 응답(예: 410 Gone)을 수신하면, 시스템은 해당 구독 정보를 자동으로 비활성화하거나 삭제하여 데이터 정합성과 발송 비용을 절감한다.

**Why this priority**: 만료 구독이 누적되면 불필요한 발송 시도와 비용이 발생하므로 자동 정리가 필요하나, 핵심 기능 이후 처리 가능하다.

**Independent Test**: 만료된 구독 엔드포인트로 발송 시도 후 해당 구독이 DB에서 비활성 처리되었는지 확인으로 독립 검증 완료.

**Acceptance Scenarios**:

1. **Given** 외부 푸시 서비스가 구독 만료(410 Gone) 응답을 반환했을 때, **When** 발송 모듈이 해당 응답을 처리하면, **Then** 해당 구독 레코드를 비활성화하고 이후 발송 대상에서 제외한다.
2. **Given** 비활성화된 구독에 대해 사용자가 다시 알림을 허용하면, **When** 새 구독 정보가 등록되면, **Then** 기존 비활성 레코드를 갱신하거나 새 레코드를 생성하여 정상 발송 대상으로 복원한다.

---

### Edge Cases

- 한 사용자가 여러 기기(PC 브라우저, 모바일 Chrome, iOS Safari)에서 동시에 구독 중인 경우, 모든 활성 구독에 알림이 병렬 발송되어야 한다.
- 알림 페이로드 크기가 외부 서비스 제한(일반적으로 4KB)을 초과하는 경우, 발송 전에 페이로드를 안전하게 잘라내거나 오류를 반환해야 한다.
- VAPID 키 쌍이 교체되는 경우, 기존 구독자가 재구독 없이도 알림을 수신할 수 있어야 하며, 키 교체 전략이 문서화되어야 한다.
- 동일한 이벤트로 인해 중복 알림 발송 요청이 큐에 적재되는 경우, 중복 발송을 방지하는 멱등성(Idempotency) 보장 메커니즘이 동작해야 한다.
- 발송 큐 브로커가 일시적으로 다운된 경우, 이벤트가 유실되지 않고 브로커 복구 후 정상 처리되어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 VAPID V2 표준 규격의 공개키/비밀키 쌍을 생성·저장하고, 모든 웹 푸시 요청에 해당 키로 서명된 JWT를 포함해야 한다.
- **FR-002**: 시스템은 사용자별 푸시 구독 정보(엔드포인트 URL, p256dh 공개키, auth 시크릿)를 등록·조회·비활성화할 수 있는 관리 인터페이스를 제공해야 한다. 알림 On/Off 토글 UI는 기존 사용자 프로필/설정 페이지 내 독립 섹션으로 통합 배치하며, 신규 페이지 생성 없이 기존 레이아웃을 재사용한다.
- **FR-003**: 시스템은 알림 발송 요청을 메인 비즈니스 로직과 분리된 독립 큐(Notification Queue)에 비동기적으로 적재해야 한다.
- **FR-004**: 독립 발송 워커(Worker)는 큐에서 알림 작업을 소비하여 구독자의 플랫폼(FCM 또는 APNs)에 맞는 채널로 라우팅하여 발송해야 한다.
- **FR-005**: 발송 실패 시 지수 백오프 정책에 따라 최대 3회 자동 재시도를 수행하고, 최종 실패 시 실패 이력을 영속화해야 한다.
- **FR-006**: 외부 서비스로부터 구독 만료(410 Gone) 응답을 수신하면, 해당 구독을 자동으로 비활성화해야 한다.
- **FR-007**: 시스템은 다음 2종의 내부 이벤트 발생 시 알림 발송 큐에 자동으로 작업을 등록하는 트리거 메커니즘을 제공해야 한다: ① 영수증 처리 완료, ② 월별 누적 지출이 시스템 고정 임계값(기본 80%, 환경 설정으로만 변경 가능)을 초과하는 경우. 사용자 개별 임계값 설정 UI는 이번 범위에서 제외한다. 이벤트 유형은 향후 확장 가능한 구조로 설계하며, 추가 이벤트는 v2 백로그로 이관한다.
- **FR-008**: 발송 워커 모듈은 메인 애플리케이션과 독립적으로 기동·종료될 수 있어야 한다.
- **FR-009**: 시스템은 알림 발송 이력(수신자, 이벤트 유형, 발송 채널, 성공/실패 여부, 타임스탬프)을 30일간 보존하는 감사 로그를 저장해야 한다. 조회 대상은 운영자 어드민 전용으로 한정하며, 최종 사용자에게 직접 노온하지 않는다. 30일 초과 이력은 주기적 자동 정리로 삭제된다.
- **FR-010**: 동일한 이벤트에 대한 중복 발송 요청이 발생하더라도 동일 사용자에게 중복 알림이 도달하지 않도록 멱등성을 보장해야 한다.

### Key Entities

- **PushSubscription (푸시 구독)**: 사용자-기기 쌍의 구독 정보. 속성: 사용자 참조, 엔드포인트 URL, p256dh 공개키, auth 시크릿, 기기 유형(FCM/APNs), 활성화 여부, 등록·갱신·만료 일시.
- **NotificationTask (알림 발송 태스크)**: 큐에 적재되는 작업 단위. 속성: 수신자(구독) 참조, 알림 제목, 본문, 액션 URL, 이벤트 유형, 상태(대기/성공/실패), 시도 횟수, 최종 시도 일시.
- **NotificationLog (발송 이력)**: 완료된 발송의 감사 기록. 속성: 태스크 참조, 사용된 채널(FCM/APNs), HTTP 응답 코드, 상세 응답 메시지, 기록 일시. 보존 기간: 에코 30일 (이후 자동 삭제). 조회 대상: 운영자 어드민 전용.
- **VAPIDKeyPair (VAPID 키 쌍)**: 서명에 사용되는 공개키/비밀키. 속성: 공개키(Base64url), 비밀키(Base64url, 암호화 저장), 생성 일시, 활성화 여부.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 내부 이벤트 발생 후 사용자 기기에 알림이 도달하는 데 걸리는 총 시간이 정상 상황 기준 30초 이내여야 한다.
- **SC-002**: 외부 푸시 서비스가 정상 상태일 때 알림 발송 성공률이 99% 이상 유지되어야 한다.
- **SC-003**: 발송 워커가 중단된 후 재기동 시 큐에 쌓인 미처리 알림을 순서대로 유실 없이 처리해야 한다.
- **SC-004**: 구독 만료 응답 수신 후 60초 이내에 해당 구독이 비활성화되어 이후 발송 대상에서 자동으로 제외되어야 한다.
- **SC-005**: 알림 발송 로직 처리가 메인 API 응답 시간에 영향을 주지 않아야 한다 (비동기 분리 검증: 메인 요청 처리 완료 후 알림 큐 적재까지 50ms 이내).
- **SC-006**: FCM 및 APNs 양측 플랫폼 모두에서 발송된 테스트 알림이 정상 수신되어야 한다.
- **SC-007**: 동일 이벤트로 발송 요청이 3회 중복 발생하더라도 사용자 기기에는 1건의 알림만 도달해야 한다.

## Assumptions

- 기존 프로젝트에 Celery 비동기 워커 인프라(015-redis-celery-integration, 016-setup-celery-queue)가 이미 구축되어 있으며, 알림 전용 큐는 이 기반 위에 독립 큐 채널로 분리되어 추가된다.
- 프론트엔드(Vue.js PWA)에는 이미 서비스 워커(sw.js)가 존재하며, 해당 서비스 워커에 `push` 이벤트 핸들러를 추가하는 방식으로 클라이언트측 알림 수신을 구현한다.
- VAPID 키 쌍은 최초 1회 생성 후 환경 변수(`.env`)로 관리되며, 운영 중 동적 교체는 이번 범위에서 제외하고 추후 확장 백로그로 이관한다.
- 알림 발송 대상 이벤트는 v1에서 ① 영수증 처리 완료, ② 월별 예산 임계 초과(기본값 80%) 2종으로 확정한다. 가계부 수동 수정 저장 등 추가 이벤트는 v2 백로그로 이관하며, 이벤트 유형은 확장 가능한 구조로 설계한다.
- FCM은 Google Firebase Cloud Messaging HTTP v1 API를 사용하며, APNs는 JWT 기반 토큰 인증 방식의 HTTP/2 연결을 사용한다. FCM 서비스 계정 JSON 자격증명은 단일 환경 변수(`GOOGLE_APPLICATION_CREDENTIALS_JSON`)에 JSON 문자열로 주입하며, 파일 볼륨 마운트 방식은 사용하지 않는다. APNs는 팀 ID, 키 ID, 활성 인증 키(p8 형식)를 각각 환경 변수로 분리 주입한다.
- VAPID V2 서명은 RFC 8292 표준을 준수하며, 알림 페이로드 암호화는 RFC 8291(Message Encryption for Web Push) 규격을 따른다.
- 알림 페이로드 크기 제한은 FCM 기준 4KB를 상한선으로 적용한다.
- 구독 정보는 기존 PostgreSQL 데이터베이스에 저장하며, 별도 NoSQL 저장소는 사용하지 않는다.
- 발송 워커는 별도의 Celery 워커 프로세스(또는 컨테이너)로 격리 기동되어 메인 API 서버와 독립적으로 운영된다.
- 알림 발송 이력(NotificationLog)는 30일간 보존하며, 이후 주기적 자동 정리로 삭제된다. 조회 대상은 운영자 어드민으로 한정하며, 최종 사용자에게 발송 이력을 직접 노출하지 않는다.
- iOS Safari의 Web Push 지원은 Safari 16.4+ 기준으로 한정하며, 구형 Safari에서의 동작은 이번 범위에서 제외한다.
