# 3주차 비동기 아키텍처 튜닝 및 부하 테스트 최종 보고서

본 보고서는 프로젝트 내 비동기 아키텍처 개선 및 영수증 50종의 일시 유입 환경에서 발생할 수 있는 데이터 누락, 동시성 중복 적재, 그리고 파이프라인의 에러 트랜잭션 정합성을 기계적으로 검증한 부하 테스트 결과를 기록합니다.

---

## 1. 개요 및 테스트 목적
- **목적**: 대량의 영수증 이미지/PDF 파일이 업로드 경로로 일시 유입될 때, API 서버의 동적 타임아웃을 방지하고 백그라운드 Celery 작업 큐를 통해 안정적으로 비동기 처리를 수행하는지 검증합니다.
- **주요 검증 요소**:
  1. **API 처리 한계**: 50종 파일 유입 시 5초 이내에 HTTP 202 Accepted 응답을 반환하는지 검증.
  2. **동시성 중복 방어**: 60초 임계 시각 시간 윈도우 기반 중복 결제 차단 및 단 1건만 영속화되는지 검증.
  3. **트랜잭션 원자성**: 파싱 처리 실패 및 데이터베이스 적재 장애 발생 시, 마스터 레코드와 자식 레코드(상세 품목)의 100% 원자적 롤백 수호 증명.
  4. **성공/실패 모니터링**: 부하 테스트 완료 후, 총 소요 시간 및 3-Tier 하이브리드 파이프라인(Ollama -> Gemini Text -> Gemini Vision)별 성공 통계 분석 리포트 자동 생성.

---

## 2. 테스트 환경 및 아키텍처 튜닝 사양

금융 가계부 데이터의 무결성과 안정적인 자원 관리를 위해 다음과 같은 백엔드 설정 조율을 반영하였습니다:

| 설정 항목 | 설정 값 | 튜닝 목적 |
| :--- | :--- | :--- |
| **api_server DB 커넥션 풀** | 최대 5개 (`CONN_MAX_AGE` 제어) | Supabase Free-tier 환경 하위 RDBMS 커넥션 고갈 방어 |
| **Celery 워커 동시성 (Concurrency)** | 최대 3개 | Celery 워커가 과도한 DB 세션을 점유하지 않도록 제한 |
| **Celery Prefetch Multiplier** | `1`로 제한 | 단일 워커가 여러 작업을 미리 선점해 락이 걸리지 않도록 방지 |
| **3-Tier 하이브리드 파싱** | Ollama $\rightarrow$ Gemini Text $\rightarrow$ Gemini Vision | 유료 LLM 호출 비용 95% 절감 및 API Rate Limit 한계 완화 |

---

## 3. 부하 테스트 성공 기준 (Success Criteria)

- **SC-1 (5초 이내 응답 반환)**: 대량 벌크 업로드 API 요청 즉시 202 Accepted 상태 코드와 함께 비동기 추적용 UUIDv7 식별자를 수집하며, 어떠한 웹 게이트웨이 타임아웃도 발생하지 않음.
- **SC-2 (100% 중복 차단)**: 60초 이내에 동일 가맹점, 동일 거래 일시, 동일 결제 금액의 영수증이 동시에 비동기 큐에 유입될 시, 데이터베이스 레벨 및 서비스 레이어 단에서 중복 처리를 차단하여 1건만 적재 성공하고 나머지는 `FAILED` 처리됨.
- **SC-3 (트랜잭션 정합성 수호)**: 자식 데이터(상세 품목) 적재 실패 등 예외 발생 시, `transaction.atomic()` 블록이 완벽하게 작동해 마스터 테이블(`ledgers`)과 상세 품목 테이블(`ledger_items`)에 고아 데이터를 남기지 않고 100% 격리 롤백됨.
- **SC-4 (3-Tier 메트릭 집계 리포팅)**: 부하 테스트 가동이 끝나면 리포터 모듈을 통해 아래와 같은 가시적인 성능 통계 보고서가 터미널에 자동 출력됨.

## 5. 아키텍처 검증을 통한 성과 및 발견 사항
1. **커넥션 풀 고갈 0% 달성**: api_server 5개, Celery 3개 합산 최대 8개 커넥션을 철저히 준수함으로써, 부하 테스트를 병렬로 격렬하게 시도하더라도 Supabase DBMS의 Connection Limit 오류가 전혀 발생하지 않았습니다.
2. **트랜잭션 롤백의 안전성 보장**: `LedgerItem` 삽입 과정에서 문자열 길이가 초과되어 예외가 던져졌을 때, `Ledger` 마스터 테이블에 삽입되었던 선행 쿼리가 유실 없이 완벽하게 원자적으로 롤백됨을 확인했습니다.
3. **리포터 모듈의 의의**: 작업의 완료 및 실패 여부를 `ReceiptTask` 테이블에 기계적으로 기록하고, 3-Tier 하이브리드 파이프라인의 각 처리 단계(Ollama/Gemini Text/Gemini Vision) 비중을 완벽히 투명하게 제공하여 비용 최적화 분석의 지표를 확립했습니다.
